# 记忆机制优化方案

整理日期：2026-10-17

适用项目：study-coder

状态：设计方案，尚未实施

本文在现有工作记忆、短期记忆、长期记忆的基础上，规划写入判断、冲突处理、有效召回、知识巩固、失效与撤销机制。除“现有机制”明确列出的内容外，新增字段、组件、参数取值和管理能力均为拟议设计。

偏好继续使用自由的 `key + content` 表达，不要求预设 `language`、`name`、`format` 等业务字段。新增元数据只负责来源、作用域、版本和生命周期管理。

实施路线分为三个阶段：基础正确性与生命周期、检索与作用域、巩固维护与效果验证。第一阶段分为 1a（独立修复）和 1b（数据结构与生命周期），第二阶段分为 2a（检索）和 2b（作用域）；各批次均可独立交付。任务、依赖和验收标准见第十三节。

**当前格式约定（2026-10-18）**：按要求删除旧版记忆兼容代码。运行时只接受数据库 schema 2、短期状态版本 2、会话版本 3；新数据库直接事务建库，不再迁移 schema 0/1，不再恢复版本 1 的短期摘要或加载版本 1/2 的会话。已有数据文件不自动删除。历史交付记录保留当时结果；后续数据库结构升级仍须另行设计备份和迁移。本次清理保留事件表、验证时间、到期时间、指纹版本、作用域及适用条件字段。

## 一、现有机制与优化目标

### 1.1 现有机制

| 项目 | 当前行为 |
| --- | --- |
| 工作记忆 | 每次模型请求前，组装目标、任务状态、后台状态、近期消息、摘要及召回资料 |
| 短期记忆 | 保存历史摘要和已覆盖消息组的哈希；需要压缩时，只处理尚未摘要的旧消息 |
| 长期记忆 | 宿主 SQLite 保存 `semantic`、`episodic`、`procedural` 三类条目 |
| 常驻加载 | `always` 独立于关键词检索，默认最多选择 8 个候选、使用 256 token |
| 按需召回 | 当前请求和任务状态参与词项匹配，默认选择前 6 个候选 |
| 长期记忆预算 | 两路共用默认 1200 token，且不超过配置上下文窗口的 10% |
| 自动归档 | 一次用户请求结束后，有符合条件的工具观察时写入情景记忆 |
| 写入校验 | 检查参数、敏感信息和容量；模型创建或修改常驻条目时，需要当前用户原话作为 `evidence` |
| 去重与容量 | 同类同键更新，同类相同归一化正文复用；容量满时只淘汰最旧情景条目 |
| 作用域 | 按规范化工作区路径哈希隔离 |
| 消息身份 | 长期资料通过带边界提示的 `user` 消息注入；旧对话摘要通过 `system` 消息注入 |

### 1.2 需要补齐的能力

1. 为旧摘要、新记忆和当前请求建立一致的冲突规则。
2. 修复合法保存的常驻条目可能无法装入默认预算的问题。
3. 区分候选命中、实际注入和实际有用，建立利用情况的观测。
4. 用版本、适用条件和来源管理知识的替换与失效。
5. 将相似经历整理成带证据的知识，避免重复堆积。
6. 区分用户、项目和工作区资料。
7. 使删除影响后续召回、摘要引用和自动巩固。

目标是让记忆准确、可用、可更新、可撤销。存储数量不作为优化效果的主要指标。

## 二、目标架构

### 2.1 三层职责

| 层级 | 职责 | 更新方式 |
| --- | --- | --- |
| 工作记忆 | 当前目标、执行状态、近期对话、本次需要的资料 | 每次模型请求重新组装 |
| 短期记忆 | 当前会话的进展、决策、失败和待办 | 增量摘要旧消息 |
| 长期记忆 | 跨会话有价值的偏好、事实、经历、方法 | 显式写入、情景归档、批量巩固 |

完整对话历史继续独立保存，作为原始记录和来源依据。模型每次收到的是工作视图，不要求全部历史都进入上下文。

### 2.2 总体流程

```text
用户输入、实际工具观察
          ↓
    来源校验与候选提取
          ↓
    分类、去重、冲突处理
          ↓
       长期记忆库
       ↓       ↓
   常驻加载   相关检索
       └───┬───┘
           ↓
与短期摘要、当前状态共同进行预算分配
           ↓
        工作记忆
           ↓
       模型与工具

长期记忆库的维护流程：
巩固 → 复验 → 替代 → 失效 → 归档或删除
```

候选、归档和已替代是长期条目的状态，不增加新的记忆层。

## 三、长期条目的数据设计

### 3.1 保持内容自由表达

条目的内容部分仍采用以下形式：

```json
{
  "kind": "semantic",
  "key": "explanation-order",
  "content": "讲解函数时先说明作用、输入和输出，再按照执行顺序解释代码。",
  "tags": ["preference", "explanation"]
}
```

每条记忆表达一项可以独立更新的知识。用户身份、交流偏好、项目架构和临时任务进展不混入同一个正文。

### 3.2 通用元数据

| 维度 | 建议字段 | 用途 |
| --- | --- | --- |
| 内容类型 | `kind` | 语义、情景、程序性记忆 |
| 加载方式 | `load_policy` | 常驻或按需 |
| 作用范围 | `scope_type`、`scope_id` | 用户、项目、工作区 |
| 生命周期 | `status` | 候选、有效、待复验、已替代、归档、删除 |
| 来源 | `source_kind`、`source_refs` | 用户原话、用户操作、工具观察、模型推断或巩固结果 |
| 版本 | `revision`、`supersedes_id` | 更新、并发检查和替代关系 |
| 适用条件 | `conditions` | 与分支、文件、依赖或环境相关的条件 |
| 有效性 | `verification_status`、`verified_at`、`expires_at` | 验证状态、最近验证时间与明确失效时间 |
| 内容标识 | `digest`、`content_fingerprint`、`fingerprint_version` | 区分原始正文去重与规范化事实识别 |
| 召回表达 | `recall_text` | 用于上下文装配的简短表达 |
| 使用信息 | 注入次数、最近注入时间、反馈记录 | 衡量利用情况 |

字段不必一次全部落地，可按实施阶段迁移。必须保持以下边界：

- `always` 只控制加载方式，不提高可信程度。
- `priority` 只影响预算中的选择顺序，不覆盖当前用户要求。
- 来源真实不等于归纳正确。
- 模型给出的置信度不能替代实际验证。
- 来源身份、确认状态和验证状态由宿主绑定，不能接受模型任意声明。

### 3.3 生命周期

```text
candidate → active → stale → active
                ├→ superseded
                ├→ archived
                └→ deleted
```

| 状态 | 含义 | 默认读取行为 |
| --- | --- | --- |
| `candidate` | 已记录，但尚不适合默认使用 | 管理或明确查询时可见 |
| `active` | 可以参与正常召回 | 按加载方式和预算选择 |
| `stale` | 条件变化或有效期到达，需要复验 | 不作为已确认事实默认使用 |
| `superseded` | 已被新版本替代 | 查询历史时可见 |
| `archived` | 保留备查 | 不默认召回 |
| `deleted` | 已撤销，不再使用 | 不提供正文，不参与自动重建 |

`active` 表示符合当前使用政策，不代表所有内容都经过工具验证；模型视图仍需保留来源和验证边界。

### 3.4 存储组织

SQLite 中可以按职责组织以下逻辑数据：

1. 记忆条目及各版本。
2. 支持、派生、矛盾和替代关系。
3. 选择、注入、反馈、更新和删除事件。

1b 采用当前条目与独立版本记录的组织方式：每个作用域内同类同键保持一个逻辑条目，版本记录按条目 ID 与版本号区分。默认读取只使用当前有效版本，历史版本用于回查和替代校验，不通过向现有唯一键下直接插入两条业务记录来保留旧值。

使用统计可以由事件汇总，避免为每种统计再建立一套独立记录。事件记录默认保存编号和原因，不重复复制完整正文或工具输出。

现有 `digest` 仍用于归一化正文的完全重复检查。新增事实指纹的生成规则需要版本化，并排除随机归档编号等易变字段；撤销检查同时使用作用域和稳定来源，不能只比较整段正文哈希。详细规则见第十节。

## 四、作用域设计

### 4.1 三类作用域

| 作用域 | 适合保存 | 示例 |
| --- | --- | --- |
| 用户级 | 跨项目偏好 | 讲解函数先说明输入输出 |
| 项目级 | 共享的项目约定 | 修改后运行项目测试 |
| 工作区级 | 当前目录及本地环境事实 | 此克隆使用某个本地依赖目录 |

用户级资料不等于对所有项目具有最高优先级。明确、适用的项目或工作区约定可以覆盖用户默认偏好，当前用户请求优先。

### 4.2 项目身份与克隆共享

项目级记忆使用宿主分配的稳定项目 ID。用户可以明确将多个克隆绑定到同一个项目。

不能仅凭相同 Git remote 自动合并全部记忆。不同克隆可能使用不同分支、依赖和配置；共享的项目知识与本地环境事实需要分别管理。

### 4.3 物理隔离与读取权限

延续 SQLite 的隔离方式：

- 用户资料单独保存。
- 项目资料按稳定项目 ID 保存。
- 工作区资料保留当前路径身份。

宿主决定本次允许读取哪些作用域。模型不能提交任意数据库路径、其他用户身份或未授权项目 ID。

初期默认仍写入工作区。跨作用域共享通过明确操作完成，避免项目事实自动扩散为用户资料。跨库操作不宣称具有全局原子性；单条更新和版本替换在所属库内完成事务。

## 五、写入机制

### 5.1 用户明确设置

用户直接管理记忆，或明确表达长期约定时，可以生成有效语义或程序性条目。

例如：

```text
以后解释函数时，先说明输入输出。
```

保留现有 `evidence` 校验，同时明确它只验证引文来自当前用户输入，不能证明长期意图被正确理解。

来源判断还应区分用户直接表达的要求与用户粘贴、引用的资料。引用材料中的指令不能直接算作用户长期授权。

自然语言理解仍需要模型参与。宿主负责来源、权限、状态和版本等可验证约束；含糊表达先进入候选，明确设置走正常流程，不对每条偏好增加一次额外确认。

### 5.2 模型主动记录

模型提出值得复用的知识，宿主依次检查：

1. 参数、长度和敏感信息是否合法。
2. 来源是否存在，是否属于本次允许使用的材料。
3. 作用域是否获得授权。
4. 是否与已有条目同键、正文完全重复，或具有明确的替代、冲突标记。
5. 是否具备生效或常驻资格。
6. 当前版本是否仍与更新依据一致。

工具返回应分别说明存储状态与生效状态，例如：

```text
已保存为候选
已生效
已替换旧版本
已保存，但未获得常驻资格
版本冲突，需要重新读取
```

不能只返回笼统的 `saved=true`，让模型误报偏好已经稳定生效。

写入和删除采用不同的返回结构，截断回退也保留操作语义。写入优先保留稳定 ID、`saved`、实际 `load_policy` 和常驻资格，其他元数据可回查；删除只返回真实的 `deleted` 结果，不能返回 `saved`。当前删除结果仅 17～18 字符，低于执行器允许的最小输出预算 160 字符，因此现有删除不会触发通用截断回退；此项属于返回协议的防御性约束，不作为已复现的删除故障。

### 5.3 自动情景归档

自动归档从“末尾几个工具结果预览”改为选择本轮有后续价值的事件：

- 重要失败及其原因。
- 已成功修复并得到验证的问题。
- 影响后续任务的环境发现。
- 尚未解决的问题。

普通目录查看、重复读取文件和无新信息的成功操作，不必每次进入长期层。未完成的一轮也可以保存有价值的失败观察，但必须如实记录完成状态。

前台采集使用工具状态、已有任务元数据和有限规则选择观察，不另发模型请求评估重要性。需要语义归因或合并的部分交给第三阶段的批量维护。

情景条目需要关联任务、会话、实际工具结果、时间，以及相关文件版本或环境信息。

以下状态分别记录：

```text
命令退出成功
测试通过
构建成功
导出成功
应用到宿主成功
```

不能统一归纳为“任务成功”。Docker 内的验证应关联执行时的容器文件状态，不能用尚未同步的宿主文件状态代替。

### 5.4 去重与版本替换

保留当前同类同键更新和归一化正文去重，在此基础上增加版本机制：

1. 调用方提交更新依据的版本。
2. 宿主检查当前有效版本。
3. 在事务中将旧版本标记为已替代，写入新版本。
4. 更新记忆库修订号，使缓存失效。

版本不一致时，返回冲突，要求重新读取。避免较早开始的模型请求静默覆盖其他进程刚写入的知识。

不同 `key` 的近义内容在第三阶段的维护流程中生成合并候选，前台不为此额外调用模型，也不能只凭相似度自动覆盖。新知识的适用条件、否定限制和来源需要保留。

### 5.5 前台执行成本

长期记忆的自动读取、显式写入和当轮情景归档，不额外发起模型请求判断重复、矛盾或长期意图。模型在正常工具循环中提出记忆建议，宿主执行确定性校验；第三阶段的语义维护单独启用、单独限额。已有会话压缩摘要保持原有职责，不与长期记忆的前台检索混淆。

前台处理限定为：

- 同键查询、正文指纹检查、状态与来源校验、明确替代关系和作用域规则。
- 已有输入长度、条目数量限制内的词法检索与候选装配。
- 预算内的有限冲突说明，不做全库两两语义比较或逐条模型判别。

1b 为常用的键、`digest` 和撤销身份查询建立对应索引；已有 `digest` 列不等于已有检索索引。2a 再引入全文索引。兼容扫描受配置条目数和单条长度限制，记录耗时与候选数量，避免将扫描或调用成本隐藏在普通写入中。

## 六、冲突处理与消息权限

### 6.1 统一历史资料身份

基础 system prompt 保存固定的记忆使用规则。短期摘要和长期记忆都作为具有明确边界的历史资料提供。

优先消除目前“旧摘要通过 `system` 注入，长期资料通过 `user` 注入”的差异。摘要、召回内容和原始工具输出，都不能因为经过模型转述就获得更高权限。

该项不依赖数据库迁移，在 1a 独立交付，同时覆盖普通摘要和最终压缩摘要两条注入路径。当前请求优先等基础规则可先落地，依赖状态和版本的完整裁决在 1b 实施。

任务和后台状态可以继续提供宿主验证过的必要元数据，不能混入原始命令输出或任意错误文本。

### 6.2 偏好和工作约定

建议顺序：

```text
当前用户明确要求
    ↓
适用范围内有效的用户长期约定
    ↓
旧摘要和历史偏好记录
```

范围更具体的有效约定可以覆盖一般默认偏好。临时要求只作用于本次请求，不自动修改长期记录。

### 6.3 环境和项目事实

建议顺序：

```text
当前实际检查结果
    ↓
适用条件仍成立的已验证记录
    ↓
历史观察
    ↓
模型推断
```

`always`、高优先级、高命中次数，都不能提升事实的可信程度。

### 6.4 无法裁决的冲突

例如两个条目分别声明项目使用 Python 3.11 和 Python 3.12，没有当前证据时，生成“存在冲突，需要检查”，不能只取更新时间更晚的一条。

环境冲突优先通过工具核实。偏好冲突在必要时询问用户。未解决的冲突不应被压缩成一个确定结论继续传播。

前台按以下顺序处理可以确定的冲突：

1. 过滤无权限、已删除、已替代及不适用的条目。
2. 存在明确版本替代关系时，选择有效版本。
3. 存在明确作用域覆盖规则时，选择适用约定。
4. 仍有多个有效且明确标记为冲突的条目时，提供带来源的简短冲突说明，并计入预算。

当前数据库以 `UNIQUE(kind, key)` 约束同类同键，更新覆盖旧正文，同库内不会正常保留两条此类记录。引入版本和多作用域后，也不能把“同键不同值”直接解释成必须把两条全文都注入；已替代值不能因此重新生效。不同自由文本之间的语义矛盾检测留给第三阶段维护。

## 七、读取、检索与预算

### 7.1 区分候选召回与最终注入

```text
作用域、状态、适用条件过滤
          ↓
加载有效的常驻资料
          ↓
检索较多按需候选
          ↓
相关性排序、冲突处理、去重
          ↓
根据 token 预算选择资料
          ↓
生成实际注入内容与选择记录
```

权限与作用域过滤必须在候选数量截断之前完成，不能先选出其他项目的条目再过滤，导致合法候选丢失。

不再先取 6 条就停止搜索。初期可检索约 40 条候选，再选择最多 6 条按需资料；候选太长时继续考察后续条目。

### 7.2 可替换的检索接口

将存储筛选、分词索引、候选召回、排序和预算选择分别组织。存储层不固定唯一一种词法评分。

第一版建议采用 SQLite FTS5/BM25，并保留简单词法实现作为兼容路径。启动时检测实际运行环境是否支持 FTS5；兼容路径仍须执行相同的作用域、状态和有效性过滤。

FTS5 提供 BM25 与列权重，可以分别调整键、标签和正文的贡献。实现时注意其 BM25 返回值越小表示匹配越好。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html#the_bm25_function)

中文需要明确的预处理策略。可以先沿用双字切分，但索引和查询必须采用相同的规范化方式。不能假定默认分词自动解决中文同义词和语义匹配。

查询构造还应考虑英文词形差异、路径、文件名和代码符号。全文查询表达式需要受控生成，不能把用户文本直接当作查询语法。

2a 的默认实现采用外部内容表与触发器，业务条目保持事实来源。全文检索并不强制使用这种存储方式，本方案选择它以明确更新和删除的一致性责任。实施时需要完成以下细节：

| 项目 | 实施要求 |
| --- | --- |
| 中文双字索引 | 将正文和查询都转换为相同规则的双字词项；索引输入保留词频，不能直接把现有集合形式的 `_terms()` 当作完整 BM25 输入 |
| 索引内容 | 使用保存预处理词项的索引内容表，例如键、标签、正文三列，并建立与业务条目稳定对应的整数 `rowid` |
| 同步事务 | 业务条目与预处理内容在同一事务内更新，触发器维护 FTS 索引；触发器本身不承担中文分词 |
| 更新与删除 | 更新时移除旧词项再写入新词项；忘记条目时同步清除可检索内容，不能留下失效索引 |
| 既有数据 | 迁移时回填预处理内容并初始化或重建全文索引；只创建触发器不会索引已有条目 |
| 列权重 | 为键、标签、正文分别配置并记录权重，使用固定检索场景验证；更改分词规则时需要重建索引 |
| 读取边界 | 全文候选仍通过业务条目的状态、权限和适用性过滤，再执行最终数量截断 |

SQLite 对外部内容表要求调用方保持索引同步，触发器只处理创建后的变更；已有记录需要另行建立索引。[SQLite 外部内容表说明](https://www.sqlite.org/fts5.html#external_content_tables)

### 7.3 查询与排序

查询依据包括：

- 当前用户请求。
- 当前子任务。
- 相关文件或代码符号。
- 有限的近期错误线索。

不直接拼接整段工具日志。

排序以相关性为基础，再适度考虑适用条件、验证状态、任务与记忆类别的匹配、时间、明确反馈和内容重复程度。

不能固定认为语义记忆总比情景记忆重要。调试历史故障时，情景记录可能更有价值。

不同库的原始相关性分数不直接混用；跨作用域检索应采用经过校准的分数或排名融合。

命中次数只作为有限参考，不能不断推高条目排名，形成早期条目长期占位的循环。

### 7.4 完整内容与召回表达

每条记忆保留两种表达：

```text
content：完整内容
recall_text：用于上下文的简短表达
```

`recall_text` 必须保留否定、条件、时间和适用范围，不能简单按字符截断。需要细节时，模型通过读取工具查看完整条目。

该字段与完整读取能力在 1b 引入。1a 先对现有正文的实际常驻消息进行预算检查，不为生成或保存简短表达提前迁移数据库。

### 7.5 预算建议

以下是待评测的初始参数，不代表已经验证的最优值，也不是现有配置已经支持的完整参数集。

| 项目 | 建议起点 |
| --- | --- |
| 长期记忆总预算 | 保留 1200 token |
| 常驻资料预算 | 试用 512 token |
| 按需候选数 | 约 40 |
| 最终按需条目数 | 最多 6 |
| 常驻数量上限 | 保留 8 |

常驻资料按实际占用扣减总预算，未使用额度交给按需资料。预算包括说明文字、条目结构和实际正文，不能只计算正文。

字符长度用于限制存储，token 预算用于限制模型输入，两者同时保留。常驻可装入性检查使用与装配共用的序列化结构、边界提示和估算函数，有效预算同样取总预算与常驻预算的较小值。不能只估算正文，也不将本地估算描述成模型真实 tokenizer 的精确计数。

公共写入入口共用预算校验，覆盖模型工具和 CLI。预算助手应独立于 SQL 存储和上下文对象，避免存储层反向依赖 `ContextManager`。

1a 不增加候选或激活状态列，采用以下写入政策：

1. 先验证请求参数、常驻类型与用户来源要求，再检查常驻预算。
2. 新条目无法独立装入常驻预算时，保存为 `on_demand`，明确返回请求方式、实际方式和未成为常驻的原因。
3. 修改已有常驻条目时，如果新内容无法独立装入，拒绝本次更新并保留原内容和加载方式。
4. 不能以 `always` 落库，再仅靠返回字段声称其未激活；没有持久状态就不能保证后续读取遵守该声明。

新增超预算条目的返回示意：

```json
{
  "saved": true,
  "requested_load_policy": "always",
  "load_policy": "on_demand",
  "activated_as_always": false,
  "reason": "core_budget_exceeded"
}
```

`on_demand` 条目仍可被相关检索召回，因此不能描述为“完全未生效”。1b 有了 `recall_text` 后，改为检查该表达并提供完整读取；若需要保存待调整的常驻建议，再使用实际持久化的候选状态明确表示。

多条常驻资料合计超限时，应列出未加载条目和原因。常驻加载也必须服从整体上下文容量。

### 7.6 读取缓存

缓存键至少覆盖：

```text
当前请求与子任务
允许读取的作用域
相关文件和错误线索
记忆库修订号
预算配置
```

写入、替换、删除、切换作用域后，下一次请求重新装配。避免同一任务反复全量检索，也避免缓存继续提供已撤销资料。

## 八、工作记忆与短期摘要

### 8.1 保留增量摘要

继续保留完整原始历史、摘要覆盖哈希和新增旧消息的增量处理。最新用户请求保留原文，助手工具调用及对应结果作为完整组处理。

截断或不完整的摘要不能提交为有效摘要。摘要失败可以回退到有限的规则摘要，但不能把失败结果当成已验证知识。

覆盖哈希针对原始消息组，不包含摘要正文。摘要文本可以更新，不能把它描述为被历史哈希锁死。为了过滤撤销资料而修改原始历史，才会使旧覆盖键失配；装配期过滤必须操作副本。

### 8.2 摘要保存工作进展

摘要重点记录：

```text
目标
已作出的决策
已经修改的内容
实际验证结果及限制
失败和待办
尚未验证的假设
```

长期偏好尽量保存为记忆引用，不再复制成一份永久规则。1b 选择“保存引用，装配期解析”的路线，而不在每次记忆更新后重算全部旧会话摘要。

引用采用可校验的结构，并区分当前默认约定与历史事件：

| 引用类型 | 解析规则 |
| --- | --- |
| 当前偏好或默认规则 | 解析该逻辑条目的当前有效版本，受作用域和替代关系约束 |
| 历史事实或历史验证 | 绑定当时版本与来源，不用新版本悄悄改写过去发生的事情 |
| 已删除、失效或不可访问的引用 | 提供不可用或待核验状态，不恢复正文 |

宿主校验引用 ID、版本和允许的作用域，模型生成的编号不自动成为有效引用。解析后的内容参与最终预算；持久化仍保存摘要模板和引用，不把展开结果写回原始历史。

记忆更新时，使相关的解析缓存失效。摘要覆盖范围继续依据原始消息校验，不能把数据库修订号变化直接当作原始历史被改写。

旧版纯文本摘要不再恢复；当前会话中的完整历史仍可重新建立短期摘要，不自动把摘要偏好写入长期层。

### 8.3 统一上下文预算

预算覆盖基础提示、技能、任务与后台状态、工具定义、常驻与按需资料、摘要和近期消息，同时为输出和估算误差保留空间。

实际运行窗口与配置不一致时，明确记录采用的预算依据。无法获知实际窗口时，也不能把配置值描述成模型服务器已确认的容量。

上下文压力大时，先减少可选资料和旧工具输出，保留当前请求、必要状态及完整工具组。

### 8.4 注入位置实验

先保持现有位置，完成权限和冲突修复，再比较“历史之前”和“最新用户请求附近”两种位置。

两组使用相同模型、条目、预算和场景，检查偏好遵守、当前要求覆盖旧偏好、冲突裁决、错误执行历史指令、延迟及可观测缓存情况。

临时记忆消息不写回原始历史，防止下次摘要再次吸收召回内容形成循环。最新用户请求的定位依据真实会话记录，不能把临时注入的资料误认为新的用户输入。

## 九、巩固、衰减与归档

### 9.1 批量巩固

初期由显式维护命令触发，稳定后再允许在任务间空闲时运行。每批处理一个作用域内数量有限的相似条目。

```text
读取待整理条目及版本
          ↓
生成合并或提炼建议
          ↓
验证来源、适用条件和反例
          ↓
再次检查版本与删除状态
          ↓
事务提交
```

模型生成建议期间不持有数据库写锁。维护有独立的条目数、输入输出、耗时和额外模型调用预算；前台任务优先。

### 9.2 证据与反例

例如：

```text
经历 A：依赖安装失败。
经历 B：发现代理白名单缺少域名。
经历 C：修改白名单后安装成功。
```

可以形成附带适用条件的代理排查步骤，并保留 A、B、C 的来源及当时环境。

同一个失败重复三次不能自动算三份独立证据。相似度高也不意味着可以忽略反例。巩固结果默认按需加载，不自动升级为常驻规则。

### 9.3 失效策略

| 内容 | 建议策略 |
| --- | --- |
| 用户明确的长期偏好 | 不因长期未命中而过期 |
| 环境、版本、文件事实 | 条件变化后标记待复验 |
| 历史测试和构建结果 | 始终绑定当时版本 |
| 程序性步骤 | 关联适用条件，变化后复验 |
| 普通情景记录 | 随时间降低默认召回机会，允许归档 |
| 模型推断 | 较短候选保留期，需要证据后生效 |

时间衰减影响召回机会，不表示事实随时间逐渐变假。用户明确给出有效期的约定，按该有效期处理。

### 9.4 容量管理

有效条目、候选、归档、事件日志分别设置条数、字节数或保留期限制。归档也必须有边界，避免将堆积转移到另一个位置。

语义或程序性记忆占满时，先整理候选、已替代和失效条目，再提示用户处理。不能为继续保存普通经历而随意淘汰明确偏好。

自动归档因容量受限失败时，记录原因，不将普通编码任务误判为失败。

## 十、删除、撤销与持久化可靠性

### 10.1 区分操作

| 操作 | 行为 |
| --- | --- |
| 归档 | 不默认使用，保留正文备查 |
| 忘记 | 撤销条目，清除可召回内容和索引 |
| 替换 | 新版本生效，保留明确替代关系 |

### 10.2 防止同源重建

删除后保留不含正文的最小撤销标记，区分以下身份：

| 身份 | 用途 |
| --- | --- |
| 条目 ID 与版本 | 撤销某条记录或某个版本 |
| 稳定来源引用 | 阻止同一批旧会话或工具事件被重放、巩固后再次写入 |
| 规范化事实指纹 | 辅助识别排除易变字段后的重复事实，并记录指纹规则版本 |

当前情景键的来源字符串含每次运行的随机 UUID；正文又包含工具调用编号，所以现有正文 `digest` 也可能随 `call_id` 变化。随机键、整段来源字符串、原始正文摘要均不能单独作为可靠的撤销身份。

稳定来源引用绑定已持久化的会话或事件位置，重放时沿用，不重新附加随机运行标识。事实指纹排除归档编号和调用追踪字段等易变内容，同时保留决定事实含义的条件、结果和必要环境信息，并结合作用域、类型使用。

撤销默认针对原条目及同源派生，不能因为内容相似就永久禁止新的独立观察。需要分别处理：

- 同一批旧来源重放或再次巩固：阻止重新激活已撤销内容。
- 用户之后明确重新设置：建立新的有效记录，并保留新的来源依据。
- 新执行中再次发生同类失败：作为新事件判断记录价值，不因旧记录被删除而一律屏蔽。

指纹只能辅助完全或规范化重复检查，不能保证识别所有近义改写。需要语义检查的情况留给第三阶段的受控维护与行为评测，不能据此宣称实现了语义层面的彻底遗忘。

### 10.3 同步处理工作视图

删除或替换后，同时处理：

- 读取缓存。
- 摘要中的记忆引用。
- 历史记忆工具结果在模型视图中的对应条目。
- 后续巩固输入。

原始历史保留完整工具调用与结果。先从原始历史定位当前用户请求：本轮记忆调用保留真实的 assistant/tool 协议、参数和回执；过去的记忆调用及对应结果整对转换为有边界的 user 资料，省略写入正文、证据参数和旧的保存成功回执。历史资料必须位于当前请求之前，不能作为 assistant 发言，也不能成为新的用户请求。只展开有效知识的必要字段，候选正文不自动召回。

混合批次只移出历史或失效的记忆调用及结果，其余调用 ID、参数和结果顺序保持不变，不单独删除某条 tool 消息，也不制造含占位参数的伪调用。同一轮发生删除、替换或库不可用时，先前的失效回执与参数也按整对移出，过滤后的资料放在真正的当前请求之前；后续真实操作回执继续保留。生成的历史资料使用仅存在于视图的类型标记，继续计入工具输出裁剪预算；普通用户输入即使包含同样的文本前缀也不被误裁剪。

模型只可依据本轮 memory_remember 的真实成功回执声称完成写入。历史资料中的知识、版本和状态用于参考，不能证明当前请求已经执行。

已经被会话保存的内部记忆块回显属于未经工具确认的 assistant 文本。装配时省略该回显，不解析其中的 JSON，不将其作为可信引用或写入证明；原始会话仍保留原文。

投影必须区分调用失败、合法空查询、读取不到条目、引用不可用和结果格式错误。安全错误信息用于修正请求；未知诊断不复制潜在旧正文，但仍明确标记为失败。不能把这些不同结果统一替换成“无引用，请重新查询”。

普通记忆更新和删除按以下顺序处理：

```text
读取 Agent.history 原始消息
          ↓
基于原始消息分组并校验摘要覆盖哈希
          ↓
创建供模型使用的视图副本
          ↓
解析引用、过滤撤销条目、保留工具组结构
          ↓
最终估算预算并校验消息协议
```

摘要器处理新增旧消息时，也使用经过撤销过滤的输入副本；覆盖哈希仍计算原始消息。不能因摘要再次读取旧记忆工具结果，将已撤销正文重新带回新摘要。

过滤和引用解析不能原地修改历史消息、工具参数或摘要覆盖键。正常增量摘要仍可推进覆盖边界，但新增覆盖键必须来自原始消息。引用展开可能增加输入长度，必须发生在最终预算检查之前。验收时比较操作前后的原始消息哈希，并确认未因副本过滤触发整份摘要失效。

原始会话是否清理属于另外明确的删除范围。不能把长期库删除描述成全部历史已经抹除；原始会话保留时，撤销记录仍应影响后续默认偏好的判断。

### 10.4 数据库与迁移

使用短事务、版本检查、有限重试和可恢复迁移。WAL 可以改善读写并行，但仍只有一个写入者，不能代替并发写入管理。[SQLite WAL 文档](https://www.sqlite.org/wal.html#concurrency)

是否启用 WAL，应结合实际 SQLite 运行时版本与本地文件系统检查。模型调用和与落盘无关的长计算在事务外执行；索引回填与重建使用边界明确的维护事务并记录耗时，避免前台长期占锁。

迁移前使用 SQLite 一致性备份，避免直接复制正在变化的数据库文件。[SQLite Backup API](https://www.sqlite.org/backup.html)

当前运行时只初始化空库或读取 schema 2；旧 schema 明确拒绝。下表用于保留当前格式数据及约束后续结构升级，不再提供 schema 0/1 的自动迁移：

| 项目 | 数据政策 |
| --- | --- |
| 当前条目状态 | 保留三类条目的状态、加载方式和工作区隔离，不通过重新打开数据库改变状态 |
| 来源和验证 | 保留已有来源；来源不足仍为未知，不伪造用户确认、工具验证或 `verified_at` |
| 时间 | 保留原始创建与更新时间，不把初始化或后续结构升级时间当作最近验证时间 |
| 常驻资料 | 不根据正文自动提升加载方式，也不把工作区偏好自动转为用户级 |
| 条目配额 | 1b 延续原有当前逻辑条目上限，版本、撤销标记和事件不重复计入该上限，并设置各自的基础容量边界 |
| 分状态配额 | 第三阶段启用；已有存量超过新目标时记录超额情况，保留读取和更新，不在迁移时直接删除或强制降级 |

`active` 只表示继续参与资料召回，不意味着历史情景被验证为当前事实。已有 1000 条时，迁移和版本替换不应因为新增了版本行就把当前逻辑条目数错误计为超限。

新写入继续受实际容量政策约束；旧存量超出后续新配额时，通过明确的整理或新增限制处理，并提供诊断，不能阻止会话启动，也不能将自动情景归档受限转化为普通任务失败。

索引可重建，正文和来源数据是恢复依据。数据库损坏或读取失败时保留现场、明确降级，不自动删除数据库。

## 十一、观测与管理接口

### 11.1 选择与使用事件

区分以下事件：

```text
被召回
被过滤
因冲突跳过
因预算跳过
实际注入
收到明确反馈
被替换或删除
```

默认日志打印原因和统计，不重复输出完整正文：

```text
[记忆] 常驻：有效 5 项，注入 4 项，预算跳过 1 项
[记忆] 按需：候选 32 项，注入 5 项
[记忆] 跳过某条资料：适用环境已变化
[记忆] 条目更新：第 2 版 → 第 3 版
```

候选命中和实际注入不等于有帮助。常驻条目天然具有高注入次数，不能据此无限增加权重。

### 11.2 模型工具

| 工具 | 职责 |
| --- | --- |

| `memory_forget` | 按授权撤销条目 |

来源身份、验证状态、确认状态不接受模型任意填写。模型自报“有帮助”可以作为模型反馈记录，不能当作用户确认或成功验证。

### 11.3 用户管理能力

建议提供以下能力，具体命令语法在实施时确定：

- 查看有效条目、候选和冲突。

- 修改加载方式和作用域。
- 接受或拒绝候选。
- 归档、删除、撤销最近一次修改。
- 手动触发巩固。
- 查看记忆利用统计。

2. 实现同一作用域内的语义重复、矛盾检查和批量巩固，生成合并或提炼建议，检查来源、反例、适用条件和证据独立性；提交前重新检查版本与删除状态。这些额外模型调用只在受控维护中发生。
3. 建立不同内容的失效和复验策略。环境变化影响相关事实与步骤，历史测试绑定当时版本，用户明确长期偏好不因未命中而自动过期。
4. 实现有效、候选、归档、事件和总字节的容量管理，采用第 10.4 节的旧存量兼容政策，优先整理失效和已替代条目；无法维护时明确降级，不破坏有效知识。
5. 提供手动维护入口和独立的耗时、输入输出及模型调用预算。手动流程稳定后，再允许任务间空闲时运行；模型生成期间不持有写锁，前台任务优先。
6. 在相同模型、资料和预算下比较注入位置，评测偏好遵守、冲突处理、过期引用、删除后继续对话及额外成本，据结果调整预算、权重和维护阈值。

**交付内容**：

- 有来源和版本约束的情景筛选、巩固与复验流程。
- 分类失效、衰减、归档和容量政策。
- 可中断、可恢复、预算受控的维护入口。
- 注入位置与记忆效果的实验记录、最终参数依据。

**验收标准**：

- 重复失败不被当成独立成功证据，也不被提炼成无条件的常驻规则。
- 合并结果可以回查支持来源、反例、适用条件和被替代条目。
- 被删除资料不能通过同源巩固重建，维护与前台更新冲突时能够停止提交或重试。
- 失效与归档区分内容类型，容量受限时不随意淘汰明确偏好。
- 维护中断、模型失败和版本冲突不破坏已有有效条目，不把普通编码任务误判为失败。
- 实际模型评测覆盖第十四节的行为场景，效果与调用成本分别报告；没有测量的策略不宣称优于现有实现。

### 13.4 迁移与启用原则

第一阶段完成当前工作区内的正确性和生命周期；第二阶段开放跨作用域读取和共享；第三阶段增加自动整理和维护。每阶段有独立交付与验收结果，可以在该阶段结束后使用和观察。

1a、1b、2a、2b 是顶层阶段内的交付批次，各自具有独立验收和发布记录。先完成 1a 的权限与预算修复，再完善当前数据结构并实施依赖状态和版本的完整裁决；检索升级和作用域共享分别启用，便于归因和回滚。

每次数据库迁移前备份。新检索和巩固策略可先旁路记录选择或合并建议，再启用实际装配或写入。回滚依赖备份和明确的版本策略，不能让旧程序强行读取不支持的新数据库格式。

## 十四、验证方案

### 14.1 确定性检查

以下约束由程序保证：

1. 不读取未授权作用域。
2. 模型不能伪造来源和确认状态。
3. 旧版本更新不能静默覆盖新版本。
4. 删除、替换后缓存失效。
5. 工具调用组保持完整。
6. 实际装配内容不超本地预算。
7. 截断摘要不提交为有效摘要。
8. 维护失败不破坏有效条目。
9. 已删除来源不能被同源巩固重新激活。
10. 初始化、并发和维护中断后可以恢复。
11. 过滤副本和解析引用不修改原始历史，也不因摘要正文变化误判覆盖哈希失配。
12. 不为长期记忆的前台读写额外发起语义判断模型请求。
13. 当前格式的满容量数据可以读取和更新，不被版本行或新状态配额错误阻断。

参数校验、权限、事务和消息结构适合单元与集成检查。它们不能替代实际模型对语义和偏好的行为评测。

需要单独覆盖的边界用例如下：

| 用例 | 主要检查 | 批次 |
| --- | --- | --- |
| 普通摘要与最终压缩 | 两条注入路径的权限边界一致，工具组仍有效 | 1a |
| 常驻预算与写入入口 | 计入 JSON 和说明文字，CLI 与模型工具一致；新增降为按需、既有超预算更新保留旧值 | 1a |
| 最小工具输出预算 | 删除在 160 字符预算下返回真实结果；写入截断回退保留实际加载方式与常驻资格 | 1a |
| 原始覆盖键与副本过滤 | 原始消息哈希不变；修改摘要文本或过滤视图不触发无关的整份摘要清除 | 1a、1b |
| 引用类型与最终预算 | 当前约定使用有效版本，历史事实保留当时版本，撤销引用不恢复正文，展开后重新检查预算 | 1b |
| 正文哈希与事实指纹 | 工具调用编号变化可以使现有正文 `digest` 变化；新的事实指纹不把追踪字段当作事实本身 | 1b |
| 同源撤销与新事件 | 同一旧来源重放被阻止，新发生的独立同类事件和用户明确重新设置分别判断 | 1b、第三阶段 |
| 满容量当前库 | 分别构造 1000 条情景、1000 条语义或程序性、混合条目的当前库，检查启动、读取与更新；后续配额收紧保护存量 | 1b、第三阶段 |
| 版本配额与建库恢复 | 新版本不增加当前逻辑条目数；保留原时间与验证状态，建库中断可重试，旧格式不被改写 | 1b |
| FTS 既有数据与同步 | 初始化后能查询旧条目，新增、更新、替代、忘记与重建后业务读取和索引一致 | 2a |
| 作用域与兼容检索 | 未授权库不可访问，FTS5 兼容路径和缓存也执行相同过滤 | 2b |
| 前台与维护调用预算 | 用调用计数区分现有会话摘要、正常工具循环和记忆维护；前台自动记忆处理不新增模型调用，维护调用有独立上限 | 各批次 |

### 14.2 模型行为场景

建立固定场景集，覆盖：

- 临时要求与长期偏好的区分。
- 当前请求覆盖长期默认偏好。
- 新记忆与旧摘要冲突。
- 用户原话包含引用或粘贴资料。
- 中文同义表达和代码符号检索。
- 相似经历中存在反例。
- 环境变化后旧方法失效。
- 删除后继续对话。
- 多作用域存在相似条目。
- 常驻和按需资料在小窗口下竞争预算。
- 满容量当前库继续任务，历史情景没有被误当成当前验证事实；旧格式被拒绝且保留原文件。
- 忘记旧经历后发生新的同类事件，既不恢复旧派生知识，也不一律屏蔽新观察。
- 明确替代、具体作用域覆盖和真正未决冲突同时存在，模型不把所有同键资料视作并列有效。

### 14.3 效果与成本指标

```text
召回准确率与覆盖率
无关资料注入率
过期资料引用率
偏好遵守率
冲突裁决正确率
额外 token 与模型调用成本
读取和维护延迟
```

注入位置、检索权重、预算和巩固阈值根据这些结果调整。比较时保持模型、场景、条目和预算可比，区分确定性程序保证与模型行为的统计结果。

## 十五、端到端示例

用户明确设置用户级偏好：

```text
以后讲函数先说明输入输出。
```

目标行为如下：

1. 保存来源可追溯的语义记忆，并生成能装入预算的常驻表达。
2. 换到其他已绑定该用户资料的项目，偏好仍能加载。
3. 用户说“这次直接给代码”，只覆盖本次请求，不修改长期偏好。
4. 用户后来明确改变长期讲解方式，新版本替代旧版本。
5. 旧摘要中的原偏好不能覆盖新版本。
6. 用户要求忘记后，缓存、记忆引用和后续巩固尊重这次撤销。

对于项目经历，例如依赖下载失败、代理配置修复和重新安装成功，系统先保存带来源的情景观察，再根据证据形成附有适用条件的排查方法。该方法按需召回，不自动成为跨项目常驻指令。

## 十六、方案边界

- 自然语言长期意图、近义冲突和语义遗忘无法仅靠格式检查保证正确，需要行为评测和可撤销的状态管理。
- BM25 改善词法排序，不自动解决同义词、跨语言或复杂语义推理。
- 资料被注入不代表模型一定采用，也不代表它帮助完成了任务。
- 历史验证只能证明当时版本和环境中的结果。
- 长期库删除不等于原始会话、备份和所有历史副本同时删除。
- 预算、候选数量和维护频率是实验起点，不能在没有测量时宣称最优。
- 前台长期记忆处理不额外调用模型，语义维护在第三阶段独立启用和限额；这一约束不取消现有会话摘要调用。

第一阶段通过 1a、1b 分别交付独立修复和当前数据结构与生命周期；第二阶段通过 2a、2b 分别交付检索与作用域；第三阶段建立受控的语义维护，并通过实验验证效果。
