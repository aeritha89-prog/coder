# 记忆机制优化方案

整理日期：2026-10-17

适用项目：study-coder

状态：设计方案，尚未实施

本文在现有工作记忆、短期记忆、长期记忆的基础上，规划写入判断、冲突处理、有效召回、知识巩固、失效与撤销机制。除“现有机制”明确列出的内容外，新增字段、组件、参数取值和管理能力均为拟议设计。

偏好继续使用自由的 `key + content` 表达，不要求预设 `language`、`name`、`format` 等业务字段。新增元数据只负责来源、作用域、版本和生命周期管理。

实施路线分为三个阶段：基础正确性与生命周期、检索与作用域、巩固维护与效果验证。每个阶段的任务、交付内容和验收标准见第十三节。

## 一、现有机制与优化目标

### 1.1 现有机制

| 项目 | 当前行为 |
| --- | --- |
| 工作记忆 | 每次模型请求前，组装目标、任务状态、后台状态、近期消息、摘要及召回资料 |
| 短期记忆 | 保存历史摘要和已覆盖消息组的哈希；需要压缩时，只处理尚未摘要的旧消息 |
| 长期记忆 | 宿主 SQLite 保存 `semantic`、`episodic`、`procedural` 三类条目 |
| 常驻加载 | `always` 独立于关键词检索，默认最多选择 8 个候选、使用 256 token |
| 按需召回 | 当前请求和任务状态参与词项匹配，默认选择前 6 个候选 |
| 长期记忆预算 | 两路共用默认 1200 token，且不超过配置上下文窗口的 10% |
| 自动归档 | 一次用户请求结束后，有符合条件的工具观察时写入情景记忆 |
| 写入校验 | 检查参数、敏感信息和容量；模型修改常驻条目时，需要当前用户原话作为 `evidence` |
| 去重与容量 | 同类同键更新，同类相同归一化正文复用；容量满时只淘汰最旧情景条目 |
| 作用域 | 按规范化工作区路径哈希隔离 |
| 消息身份 | 长期资料通过带边界提示的 `user` 消息注入；旧对话摘要通过 `system` 消息注入 |

### 1.2 需要补齐的能力

1. 为旧摘要、新记忆和当前请求建立一致的冲突规则。
2. 修复合法保存的常驻条目可能无法装入默认预算的问题。
3. 区分候选命中、实际注入和实际有用，建立利用情况的观测。
4. 用版本、适用条件和来源管理知识的替换与失效。
5. 将相似经历整理成带证据的知识，避免重复堆积。
6. 区分用户、项目和工作区资料。
7. 使删除影响后续召回、摘要引用和自动巩固。

目标是让记忆准确、可用、可更新、可撤销。存储数量不作为优化效果的主要指标。

## 二、目标架构

### 2.1 三层职责

| 层级 | 职责 | 更新方式 |
| --- | --- | --- |
| 工作记忆 | 当前目标、执行状态、近期对话、本次需要的资料 | 每次模型请求重新组装 |
| 短期记忆 | 当前会话的进展、决策、失败和待办 | 增量摘要旧消息 |
| 长期记忆 | 跨会话有价值的偏好、事实、经历、方法 | 显式写入、情景归档、批量巩固 |

完整对话历史继续独立保存，作为原始记录和来源依据。模型每次收到的是工作视图，不要求全部历史都进入上下文。

### 2.2 总体流程

```text
用户输入、实际工具观察
          ↓
    来源校验与候选提取
          ↓
    分类、去重、冲突处理
          ↓
       长期记忆库
       ↓       ↓
   常驻加载   相关检索
       └───┬───┘
           ↓
与短期摘要、当前状态共同进行预算分配
           ↓
        工作记忆
           ↓
       模型与工具

长期记忆库的维护流程：
巩固 → 复验 → 替代 → 失效 → 归档或删除
```

候选、归档和已替代是长期条目的状态，不增加新的记忆层。

## 三、长期条目的数据设计

### 3.1 保持内容自由表达

条目的内容部分仍采用以下形式：

```json
{
  "kind": "semantic",
  "key": "explanation-order",
  "content": "讲解函数时先说明作用、输入和输出，再按照执行顺序解释代码。",
  "tags": ["preference", "explanation"]
}
```

每条记忆表达一项可以独立更新的知识。用户身份、交流偏好、项目架构和临时任务进展不混入同一个正文。

### 3.2 通用元数据

| 维度 | 建议字段 | 用途 |
| --- | --- | --- |
| 内容类型 | `kind` | 语义、情景、程序性记忆 |
| 加载方式 | `load_policy` | 常驻或按需 |
| 作用范围 | `scope_type`、`scope_id` | 用户、项目、工作区 |
| 生命周期 | `status` | 候选、有效、待复验、已替代、归档、删除 |
| 来源 | `source_kind`、`source_refs` | 用户原话、用户操作、工具观察、模型推断或巩固结果 |
| 版本 | `revision`、`supersedes_id` | 更新、并发检查和替代关系 |
| 适用条件 | `conditions` | 与分支、文件、依赖或环境相关的条件 |
| 有效性 | `verified_at`、`expires_at` | 最近验证时间与明确失效时间 |
| 召回表达 | `recall_text` | 用于上下文装配的简短表达 |
| 使用信息 | 注入次数、最近注入时间、反馈记录 | 衡量利用情况 |

字段不必一次全部落地，可按实施阶段迁移。必须保持以下边界：

- `always` 只控制加载方式，不提高可信程度。
- `priority` 只影响预算中的选择顺序，不覆盖当前用户要求。
- 来源真实不等于归纳正确。
- 模型给出的置信度不能替代实际验证。
- 来源身份、确认状态和验证状态由宿主绑定，不能接受模型任意声明。

### 3.3 生命周期

```text
candidate → active → stale → active
                ├→ superseded
                ├→ archived
                └→ deleted
```

| 状态 | 含义 | 默认读取行为 |
| --- | --- | --- |
| `candidate` | 已记录，但尚不适合默认使用 | 管理或明确查询时可见 |
| `active` | 可以参与正常召回 | 按加载方式和预算选择 |
| `stale` | 条件变化或有效期到达，需要复验 | 不作为已确认事实默认使用 |
| `superseded` | 已被新版本替代 | 查询历史时可见 |
| `archived` | 保留备查 | 不默认召回 |
| `deleted` | 已撤销，不再使用 | 不提供正文，不参与自动重建 |

`active` 表示符合当前使用政策，不代表所有内容都经过工具验证；模型视图仍需保留来源和验证边界。

### 3.4 存储组织

SQLite 中可以按职责组织以下逻辑数据：

1. 记忆条目及各版本。
2. 支持、派生、矛盾和替代关系。
3. 选择、注入、反馈、更新和删除事件。

使用统计可以由事件汇总，避免为每种统计再建立一套独立记录。事件记录默认保存编号和原因，不重复复制完整正文或工具输出。

## 四、作用域设计

### 4.1 三类作用域

| 作用域 | 适合保存 | 示例 |
| --- | --- | --- |
| 用户级 | 跨项目偏好 | 讲解函数先说明输入输出 |
| 项目级 | 共享的项目约定 | 修改后运行项目测试 |
| 工作区级 | 当前目录及本地环境事实 | 此克隆使用某个本地依赖目录 |

用户级资料不等于对所有项目具有最高优先级。明确、适用的项目或工作区约定可以覆盖用户默认偏好，当前用户请求优先。

### 4.2 项目身份与克隆共享

项目级记忆使用宿主分配的稳定项目 ID。用户可以明确将多个克隆绑定到同一个项目。

不能仅凭相同 Git remote 自动合并全部记忆。不同克隆可能使用不同分支、依赖和配置；共享的项目知识与本地环境事实需要分别管理。

### 4.3 物理隔离与读取权限

延续 SQLite 的隔离方式：

- 用户资料单独保存。
- 项目资料按稳定项目 ID 保存。
- 工作区资料保留当前路径身份。

宿主决定本次允许读取哪些作用域。模型不能提交任意数据库路径、其他用户身份或未授权项目 ID。

初期默认仍写入工作区。跨作用域共享通过明确操作完成，避免项目事实自动扩散为用户资料。跨库操作不宣称具有全局原子性；单条更新和版本替换在所属库内完成事务。

## 五、写入机制

### 5.1 用户明确设置

用户直接管理记忆，或明确表达长期约定时，可以生成有效语义或程序性条目。

例如：

```text
以后解释函数时，先说明输入输出。
```

保留现有 `evidence` 校验，同时明确它只验证引文来自当前用户输入，不能证明长期意图被正确理解。

来源判断还应区分用户直接表达的要求与用户粘贴、引用的资料。引用材料中的指令不能直接算作用户长期授权。

自然语言理解仍需要模型参与。宿主负责来源、权限、状态和版本等可验证约束；含糊表达先进入候选，明确设置走正常流程，不对每条偏好增加一次额外确认。

### 5.2 模型主动记录

模型提出值得复用的知识，宿主依次检查：

1. 参数、长度和敏感信息是否合法。
2. 来源是否存在，是否属于本次允许使用的材料。
3. 作用域是否获得授权。
4. 是否与已有条目重复或矛盾。
5. 是否具备生效或常驻资格。
6. 当前版本是否仍与更新依据一致。

工具返回应分别说明存储状态与生效状态，例如：

```text
已保存为候选
已生效
已替换旧版本
已保存，但未获得常驻资格
版本冲突，需要重新读取
```

不能只返回笼统的 `saved=true`，让模型误报偏好已经稳定生效。

### 5.3 自动情景归档

自动归档从“末尾几个工具结果预览”改为选择本轮有后续价值的事件：

- 重要失败及其原因。
- 已成功修复并得到验证的问题。
- 影响后续任务的环境发现。
- 尚未解决的问题。

普通目录查看、重复读取文件和无新信息的成功操作，不必每次进入长期层。未完成的一轮也可以保存有价值的失败观察，但必须如实记录完成状态。

情景条目需要关联任务、会话、实际工具结果、时间，以及相关文件版本或环境信息。

以下状态分别记录：

```text
命令退出成功
测试通过
构建成功
导出成功
应用到宿主成功
```

不能统一归纳为“任务成功”。Docker 内的验证应关联执行时的容器文件状态，不能用尚未同步的宿主文件状态代替。

### 5.4 去重与版本替换

保留当前同类同键更新和归一化正文去重，在此基础上增加版本机制：

1. 调用方提交更新依据的版本。
2. 宿主检查当前有效版本。
3. 在事务中将旧版本标记为已替代，写入新版本。
4. 更新记忆库修订号，使缓存失效。

版本不一致时，返回冲突，要求重新读取。避免较早开始的模型请求静默覆盖其他进程刚写入的知识。

不同 `key` 的近义内容可以生成合并候选，但不能只凭相似度自动覆盖。新知识的适用条件、否定限制和来源需要保留。

## 六、冲突处理与消息权限

### 6.1 统一历史资料身份

基础 system prompt 保存固定的记忆使用规则。短期摘要和长期记忆都作为具有明确边界的历史资料提供。

优先消除目前“旧摘要通过 `system` 注入，长期资料通过 `user` 注入”的差异。摘要、召回内容和原始工具输出，都不能因为经过模型转述就获得更高权限。

任务和后台状态可以继续提供宿主验证过的必要元数据，不能混入原始命令输出或任意错误文本。

### 6.2 偏好和工作约定

建议顺序：

```text
当前用户明确要求
    ↓
适用范围内有效的用户长期约定
    ↓
旧摘要和历史偏好记录
```

范围更具体的有效约定可以覆盖一般默认偏好。临时要求只作用于本次请求，不自动修改长期记录。

### 6.3 环境和项目事实

建议顺序：

```text
当前实际检查结果
    ↓
适用条件仍成立的已验证记录
    ↓
历史观察
    ↓
模型推断
```

`always`、高优先级、高命中次数，都不能提升事实的可信程度。

### 6.4 无法裁决的冲突

例如两个条目分别声明项目使用 Python 3.11 和 Python 3.12，没有当前证据时，生成“存在冲突，需要检查”，不能只取更新时间更晚的一条。

环境冲突优先通过工具核实。偏好冲突在必要时询问用户。未解决的冲突不应被压缩成一个确定结论继续传播。

## 七、读取、检索与预算

### 7.1 区分候选召回与最终注入

```text
作用域、状态、适用条件过滤
          ↓
加载有效的常驻资料
          ↓
检索较多按需候选
          ↓
相关性排序、冲突处理、去重
          ↓
根据 token 预算选择资料
          ↓
生成实际注入内容与选择记录
```

权限与作用域过滤必须在候选数量截断之前完成，不能先选出其他项目的条目再过滤，导致合法候选丢失。

不再先取 6 条就停止搜索。初期可检索约 40 条候选，再选择最多 6 条按需资料；候选太长时继续考察后续条目。

### 7.2 可替换的检索接口

将存储筛选、分词索引、候选召回、排序和预算选择分别组织。存储层不固定唯一一种词法评分。

第一版建议采用 SQLite FTS5/BM25，并保留简单词法实现作为兼容路径。启动时检测实际运行环境是否支持 FTS5；兼容路径仍须执行相同的作用域、状态和有效性过滤。

FTS5 提供 BM25 与列权重，可以分别调整键、标签和正文的贡献。实现时注意其 BM25 返回值越小表示匹配越好。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html#the_bm25_function)

中文需要明确的预处理策略。可以先沿用双字切分，但索引和查询必须采用相同的规范化方式。不能假定默认分词自动解决中文同义词和语义匹配。

查询构造还应考虑英文词形差异、路径、文件名和代码符号。全文查询表达式需要受控生成，不能把用户文本直接当作查询语法。

### 7.3 查询与排序

查询依据包括：

- 当前用户请求。
- 当前子任务。
- 相关文件或代码符号。
- 有限的近期错误线索。

不直接拼接整段工具日志。

排序以相关性为基础，再适度考虑适用条件、验证状态、任务与记忆类别的匹配、时间、明确反馈和内容重复程度。

不能固定认为语义记忆总比情景记忆重要。调试历史故障时，情景记录可能更有价值。

不同库的原始相关性分数不直接混用；跨作用域检索应采用经过校准的分数或排名融合。

命中次数只作为有限参考，不能不断推高条目排名，形成早期条目长期占位的循环。

### 7.4 完整内容与召回表达

每条记忆保留两种表达：

```text
content：完整内容
recall_text：用于上下文的简短表达
```

`recall_text` 必须保留否定、条件、时间和适用范围，不能简单按字符截断。需要细节时，模型通过读取工具查看完整条目。

### 7.5 预算建议

以下是待评测的初始参数，不代表已经验证的最优值，也不是现有配置已经支持的完整参数集。

| 项目 | 建议起点 |
| --- | --- |
| 长期记忆总预算 | 保留 1200 token |
| 常驻资料预算 | 试用 512 token |
| 按需候选数 | 约 40 |
| 最终按需条目数 | 最多 6 |
| 常驻数量上限 | 保留 8 |

常驻资料按实际占用扣减总预算，未使用额度交给按需资料。预算包括说明文字、条目结构和实际正文，不能只计算正文。

保存常驻条目前，检查其召回表达能否独立装入预算。无法装入时，要求更短且语义完整的表达，或明确返回“已保存，但不能激活为常驻”。不能静默跳过，却声称偏好已稳定生效。

多条常驻资料合计超限时，应列出未加载条目和原因。常驻加载也必须服从整体上下文容量。

### 7.6 读取缓存

缓存键至少覆盖：

```text
当前请求与子任务
允许读取的作用域
相关文件和错误线索
记忆库修订号
预算配置
```

写入、替换、删除、切换作用域后，下一次请求重新装配。避免同一任务反复全量检索，也避免缓存继续提供已撤销资料。

## 八、工作记忆与短期摘要

### 8.1 保留增量摘要

继续保留完整原始历史、摘要覆盖哈希和新增旧消息的增量处理。最新用户请求保留原文，助手工具调用及对应结果作为完整组处理。

截断或不完整的摘要不能提交为有效摘要。摘要失败可以回退到有限的规则摘要，但不能把失败结果当成已验证知识。

### 8.2 摘要保存工作进展

摘要重点记录：

```text
目标
已作出的决策
已经修改的内容
实际验证结果及限制
失败和待办
尚未验证的假设
```

长期偏好尽量保存为记忆引用，不再复制成一份永久规则，例如引用条目 ID 和版本。条目替换或删除后，可以识别失效引用。

对于旧版纯文本摘要，先按历史资料处理。迁移时不自动把其中的偏好重新写入长期层。

### 8.3 统一上下文预算

预算覆盖基础提示、技能、任务与后台状态、工具定义、常驻与按需资料、摘要和近期消息，同时为输出和估算误差保留空间。

实际运行窗口与配置不一致时，明确记录采用的预算依据。无法获知实际窗口时，也不能把配置值描述成模型服务器已确认的容量。

上下文压力大时，先减少可选资料和旧工具输出，保留当前请求、必要状态及完整工具组。

### 8.4 注入位置实验

先保持现有位置，完成权限和冲突修复，再比较“历史之前”和“最新用户请求附近”两种位置。

两组使用相同模型、条目、预算和场景，检查偏好遵守、当前要求覆盖旧偏好、冲突裁决、错误执行历史指令、延迟及可观测缓存情况。

临时记忆消息不写回原始历史，防止下次摘要再次吸收召回内容形成循环。最新用户请求的定位依据真实会话记录，不能把临时注入的资料误认为新的用户输入。

## 九、巩固、衰减与归档

### 9.1 批量巩固

初期由显式维护命令触发，稳定后再允许在任务间空闲时运行。每批处理一个作用域内数量有限的相似条目。

```text
读取待整理条目及版本
          ↓
生成合并或提炼建议
          ↓
验证来源、适用条件和反例
          ↓
再次检查版本与删除状态
          ↓
事务提交
```

模型生成建议期间不持有数据库写锁。维护有独立的条目数、输入输出、耗时和额外模型调用预算；前台任务优先。

### 9.2 证据与反例

例如：

```text
经历 A：依赖安装失败。
经历 B：发现代理白名单缺少域名。
经历 C：修改白名单后安装成功。
```

可以形成附带适用条件的代理排查步骤，并保留 A、B、C 的来源及当时环境。

同一个失败重复三次不能自动算三份独立证据。相似度高也不意味着可以忽略反例。巩固结果默认按需加载，不自动升级为常驻规则。

### 9.3 失效策略

| 内容 | 建议策略 |
| --- | --- |
| 用户明确的长期偏好 | 不因长期未命中而过期 |
| 环境、版本、文件事实 | 条件变化后标记待复验 |
| 历史测试和构建结果 | 始终绑定当时版本 |
| 程序性步骤 | 关联适用条件，变化后复验 |
| 普通情景记录 | 随时间降低默认召回机会，允许归档 |
| 模型推断 | 较短候选保留期，需要证据后生效 |

时间衰减影响召回机会，不表示事实随时间逐渐变假。用户明确给出有效期的约定，按该有效期处理。

### 9.4 容量管理

有效条目、候选、归档、事件日志分别设置条数、字节数或保留期限制。归档也必须有边界，避免将堆积转移到另一个位置。

语义或程序性记忆占满时，先整理候选、已替代和失效条目，再提示用户处理。不能为继续保存普通经历而随意淘汰明确偏好。

自动归档因容量受限失败时，记录原因，不将普通编码任务误判为失败。

## 十、删除、撤销与持久化可靠性

### 10.1 区分操作

| 操作 | 行为 |
| --- | --- |
| 归档 | 不默认使用，保留正文备查 |
| 忘记 | 撤销条目，清除可召回内容和索引 |
| 替换 | 新版本生效，保留明确替代关系 |

### 10.2 防止同源重建

删除后保留不含正文的最小撤销标记，关联原条目和来源身份。自动巩固不能根据同一批旧来源重新创建被删除条目。用户之后明确重新设置时，可以生成新的有效记录。

这种方式阻止同源重建，不能仅凭哈希保证识别所有近义改写；语义重建需要单独过滤和评测。

### 10.3 同步处理工作视图

删除或替换后，同时处理：

- 读取缓存。
- 摘要中的记忆引用。
- 历史记忆工具结果在模型视图中的对应条目。
- 后续巩固输入。

保留工具调用与结果结构，不直接删掉某条工具消息造成孤立调用。

原始会话是否清理属于另外明确的删除范围。不能把长期库删除描述成全部历史已经抹除；原始会话保留时，撤销记录仍应影响后续默认偏好的判断。

### 10.4 数据库与迁移

使用短事务、版本检查、有限重试和可恢复迁移。WAL 可以改善读写并行，但仍只有一个写入者，不能代替并发写入管理。[SQLite WAL 文档](https://www.sqlite.org/wal.html#concurrency)

是否启用 WAL，应结合实际 SQLite 运行时版本与本地文件系统检查。模型调用、索引重建之外的长计算，不在写事务内执行。

迁移前使用 SQLite 一致性备份，避免直接复制正在变化的数据库文件。[SQLite Backup API](https://www.sqlite.org/backup.html)

迁移保留现有加载方式和隔离范围，旧正文不自动升级为常驻或用户级资料。迁移后的来源不足部分标记为历史迁移记录，不能伪造新的用户确认。

索引可重建，正文和来源数据是恢复依据。数据库损坏或读取失败时保留现场、明确降级，不自动删除数据库。

## 十一、观测与管理接口

### 11.1 选择与使用事件

区分以下事件：

```text
被召回
被过滤
因冲突跳过
因预算跳过
实际注入
收到明确反馈
被替换或删除
```

默认日志打印原因和统计，不重复输出完整正文：

```text
[记忆] 常驻：有效 5 项，注入 4 项，预算跳过 1 项
[记忆] 按需：候选 32 项，注入 5 项
[记忆] 跳过某条资料：适用环境已变化
[记忆] 条目更新：第 2 版 → 第 3 版
```

候选命中和实际注入不等于有帮助。常驻条目天然具有高注入次数，不能据此无限增加权重。

### 11.2 模型工具

| 工具 | 职责 |
| --- | --- |
| `memory_search` | 返回简短候选及适用性说明 |
| `memory_read`（拟新增） | 查看完整内容、版本和来源 |
| `memory_remember` | 提交新增或更新建议，明确返回生效状态 |
| `memory_forget` | 按授权撤销条目 |

来源身份、验证状态、确认状态不接受模型任意填写。模型自报“有帮助”可以作为模型反馈记录，不能当作用户确认或成功验证。

### 11.3 用户管理能力

建议提供以下能力，具体命令语法在实施时确定：

- 查看有效条目、候选和冲突。
- 查看条目为什么被加载或跳过。
- 修改加载方式和作用域。
- 接受或拒绝候选。
- 归档、删除、撤销最近一次修改。
- 手动触发巩固。
- 查看记忆利用统计。

## 十三、三阶段实施计划

三个阶段顺序推进，每阶段完成验收后再进入下一阶段。第十四节的确定性检查、模型行为场景和效果指标贯穿三个阶段，不集中留到最后补测。

| 阶段 | 目标 | 主要内容 | 阶段结果 |
| --- | --- | --- | --- |
| 第一阶段 | 记忆正确生效、更新和撤销 | 资料权限、冲突规则、来源与版本、常驻预算、删除和缓存失效 | 当前工作区内的记忆具备明确状态和可追溯生命周期 |
| 第二阶段 | 相关资料可检索、可共享、可度量 | 检索接口、BM25、候选扩展、用户与项目作用域、缓存和使用统计 | 在授权范围内按预算提供相关资料，并能解释选择原因 |
| 第三阶段 | 长期知识可整理、可复验、容量可控 | 情景筛选、批量巩固、失效与归档、容量管理、注入位置和效果实验 | 形成有证据、可撤销、成本受控的记忆维护流程 |

### 13.1 第一阶段：基础正确性与生命周期

**目标**：修复现有机制中的权限和预算问题，使写入、更新、删除的结果能够正确影响后续模型请求。

**实施任务**：

1. 统一短期摘要与长期资料的消息权限。固定 system 规则负责说明当前请求、有效偏好和历史资料的关系，摘要不再因消息角色获得更高权威。
2. 实现偏好与环境事实两类冲突规则。当前临时要求只影响本次请求；新长期约定替代旧版本；缺少证据的环境冲突保留为待检查状态。
3. 增加来源引用、条目状态、版本和替代关系，预留作用域字段。现有条目迁移后仍保持工作区隔离，不自动升级为用户级资料。
4. 完善写入政策。区分明确设置、模型建议和工具观察，含糊内容可以进入候选；宿主绑定来源，不能接受模型自行声明用户确认或验证成功。
5. 增加 `recall_text` 与完整读取能力，修正常驻条目保存长度和实际注入预算不匹配的问题。无法装入时明确返回原因，保持整体上下文预算和工具消息组完整。
6. 实现带版本检查的事务更新、库修订号和后续请求的缓存失效。版本冲突返回重新读取要求，不静默覆盖新知识。
7. 实现归档、替换、忘记的基本语义。删除同步影响读取、摘要引用和记忆工具结果的工作视图，并记录供后续巩固检查的同源撤销标记。
8. 保留增量摘要、覆盖哈希和原始会话；补齐候选查看、生效状态、预算跳过等必要管理与日志能力。

**交付内容**：

- 有备份和兼容检查的数据库迁移。
- 一致的资料权限和冲突规则。
- 来源、状态、版本、替代及撤销记录。
- 可装配的记忆简短表达、完整读取能力和预算诊断。
- 更新、删除后下一次请求重新读取的机制。

**验收标准**：

- 摘要与长期资料的角色边界一致；固定冲突场景中能明确区分当前要求、有效偏好和旧记录。
- 常驻表达无法装入预算时可见原因，工具不能误报其已稳定生效。
- 候选、有效、已替代和已删除条目不会被混作同一种有效资料。
- 并发更新不会覆盖较新版本，更新和删除能影响下一次模型请求。
- 删除不破坏工具调用组，也不会被当前同源自动写入路径立即恢复。
- 会话恢复、增量摘要及现有记忆工具的必要行为通过回归检查；模型语义判断结果单独记录，不当作程序保证。

### 13.2 第二阶段：检索与作用域

**前置条件**：第一阶段的状态、来源、版本和撤销规则已可用，检索能够据此过滤条目。

**目标**：改善资料的实际利用效率，支持明确授权的跨项目偏好和项目共享，并能够观察检索与装配过程。

**实施任务**：

1. 拆分存储筛选、候选召回、排序和预算选择，建立可替换的检索接口。
2. 接入 FTS5/BM25，统一中文、英文、路径和符号的查询预处理。检测 FTS5 可用性，保留执行相同权限与有效性过滤的兼容路径。
3. 扩大候选集合，区分候选数量与最终注入数量；在预算内继续考察后续条目，加入相关性、适用性、去重和有限反馈因素。
4. 开放用户、项目、工作区三类作用域。用户资料和项目共享均由宿主绑定，多个克隆通过明确项目关联共享，环境事实仍受适用范围约束。
5. 实现按请求、子任务、相关线索、作用域、库修订号和预算配置区分的读取缓存。跨作用域候选采用可比较的排序或排名融合。
6. 记录候选、过滤、跳过、注入和反馈事件，增加原因查询与统计；缓存命中也要如实反映本次实际注入，不能等同于取得有效帮助。
7. 完善搜索、完整读取、作用域管理和条目选择原因等用户入口，建立后续维护与实验所需的基线数据。

**交付内容**：

- 可替换的检索与预算装配组件。
- FTS5/BM25 实现及能力检测、兼容路径。
- 用户资料、项目身份映射和工作区隔离。
- 可失效的读取缓存、使用事件和查询统计。
- 固定检索场景集与基线效果、成本记录。

**验收标准**：

- 授权、状态和有效性过滤在候选截断前执行，不读取未授权作用域。
- 前几个候选太长时，能够继续选择后续合适资料，并遵守总预算。
- 检索场景覆盖中文、词形差异、文件路径、代码符号和相似历史问题；用准确率、覆盖率与无关注入率评价结果。
- 用户级偏好可在明确绑定的项目间生效；不同克隆的本地环境事实不被无条件共享。
- 更新、删除和切换作用域后缓存失效；能力缺失时兼容路径仍遵守相同边界。
- 能区分候选命中、实际注入、预算跳过和明确反馈，记录读取延迟及 token 成本。

### 13.3 第三阶段：巩固维护与效果验证

**前置条件**：前两个阶段的来源、版本、作用域、撤销和使用观测已经稳定，能够判断维护输入是否仍有效。

**目标**：让长期记忆有选择地积累、整理、复验和退出，并根据实际模型表现调整策略。

**实施任务**：

1. 改进自动情景归档，选择重要失败、有效修复、环境发现和未解决问题，减少普通查看与重复成功观察的长期写入。
2. 实现同一作用域内的批量巩固，生成合并或提炼建议，检查来源、反例、适用条件和证据独立性；提交前重新检查版本与删除状态。
3. 建立不同内容的失效和复验策略。环境变化影响相关事实与步骤，历史测试绑定当时版本，用户明确长期偏好不因未命中而自动过期。
4. 实现有效、候选、归档、事件和总字节的容量管理，优先整理失效和已替代条目；无法维护时明确降级，不破坏有效知识。
5. 提供手动维护入口和独立的耗时、输入输出及模型调用预算。手动流程稳定后，再允许任务间空闲时运行；模型生成期间不持有写锁，前台任务优先。
6. 在相同模型、资料和预算下比较注入位置，评测偏好遵守、冲突处理、过期引用、删除后继续对话及额外成本，据结果调整预算、权重和维护阈值。

**交付内容**：

- 有来源和版本约束的情景筛选、巩固与复验流程。
- 分类失效、衰减、归档和容量政策。
- 可中断、可恢复、预算受控的维护入口。
- 注入位置与记忆效果的实验记录、最终参数依据。

**验收标准**：

- 重复失败不被当成独立成功证据，也不被提炼成无条件的常驻规则。
- 合并结果可以回查支持来源、反例、适用条件和被替代条目。
- 被删除资料不能通过同源巩固重建，维护与前台更新冲突时能够停止提交或重试。
- 失效与归档区分内容类型，容量受限时不随意淘汰明确偏好。
- 维护中断、模型失败和版本冲突不破坏已有有效条目，不把普通编码任务误判为失败。
- 实际模型评测覆盖第十四节的行为场景，效果与调用成本分别报告；没有测量的策略不宣称优于现有实现。

### 13.4 迁移与启用原则

第一阶段完成当前工作区内的正确性和生命周期；第二阶段开放跨作用域读取和共享；第三阶段增加自动整理和维护。每阶段有独立交付与验收结果，可以在该阶段结束后使用和观察。

每次数据库迁移前备份。新检索和巩固策略可先旁路记录选择或合并建议，再启用实际装配或写入。回滚依赖备份和明确的版本策略，不能让旧程序强行读取不支持的新数据库格式。

## 十四、验证方案

### 14.1 确定性检查

以下约束由程序保证：

1. 不读取未授权作用域。
2. 模型不能伪造来源和确认状态。
3. 旧版本更新不能静默覆盖新版本。
4. 删除、替换后缓存失效。
5. 工具调用组保持完整。
6. 实际装配内容不超本地预算。
7. 截断摘要不提交为有效摘要。
8. 维护失败不破坏有效条目。
9. 已删除来源不能被同源巩固重新激活。
10. 迁移、并发和维护中断后可以恢复。

参数校验、权限、事务和消息结构适合单元与集成检查。它们不能替代实际模型对语义和偏好的行为评测。

### 14.2 模型行为场景

建立固定场景集，覆盖：

- 临时要求与长期偏好的区分。
- 当前请求覆盖长期默认偏好。
- 新记忆与旧摘要冲突。
- 用户原话包含引用或粘贴资料。
- 中文同义表达和代码符号检索。
- 相似经历中存在反例。
- 环境变化后旧方法失效。
- 删除后继续对话。
- 多作用域存在相似条目。
- 常驻和按需资料在小窗口下竞争预算。

### 14.3 效果与成本指标

```text
召回准确率与覆盖率
无关资料注入率
过期资料引用率
偏好遵守率
冲突裁决正确率
额外 token 与模型调用成本
读取和维护延迟
```

注入位置、检索权重、预算和巩固阈值根据这些结果调整。比较时保持模型、场景、条目和预算可比，区分确定性程序保证与模型行为的统计结果。

## 十五、端到端示例

用户明确设置用户级偏好：

```text
以后讲函数先说明输入输出。
```

目标行为如下：

1. 保存来源可追溯的语义记忆，并生成能装入预算的常驻表达。
2. 换到其他已绑定该用户资料的项目，偏好仍能加载。
3. 用户说“这次直接给代码”，只覆盖本次请求，不修改长期偏好。
4. 用户后来明确改变长期讲解方式，新版本替代旧版本。
5. 旧摘要中的原偏好不能覆盖新版本。
6. 用户要求忘记后，缓存、记忆引用和后续巩固尊重这次撤销。

对于项目经历，例如依赖下载失败、代理配置修复和重新安装成功，系统先保存带来源的情景观察，再根据证据形成附有适用条件的排查方法。该方法按需召回，不自动成为跨项目常驻指令。

## 十六、方案边界

- 自然语言长期意图、近义冲突和语义遗忘无法仅靠格式检查保证正确，需要行为评测和可撤销的状态管理。
- BM25 改善词法排序，不自动解决同义词、跨语言或复杂语义推理。
- 资料被注入不代表模型一定采用，也不代表它帮助完成了任务。
- 历史验证只能证明当时版本和环境中的结果。
- 长期库删除不等于原始会话、备份和所有历史副本同时删除。
- 预算、候选数量和维护频率是实验起点，不能在没有测量时宣称最优。

第一阶段落实权限一致、更新正确、预算可用和撤销有效；第二阶段提高检索质量并开放受控共享；第三阶段建立长期维护并通过实验验证效果。
