# 增量上下文管理

## 改动目的

原实现每轮依据完整 history 判断是否压缩。历史超过阈值后，即使上一轮模型输入已降到数千 token，下一轮仍会重新进入摘要流程。

现在每轮依据以下工作上下文判断预算：

```text
基础系统提示 + 活动技能 + 已有摘要 + 未摘要消息 + 最新用户请求 + 工具 schema
```

最新用户请求保持原文；如果它已经包含在摘要覆盖范围内，仍额外保留一次原文。
已归纳的原始消息留在 history 和会话归档中，不重新加入工作上下文。

## 具体实现

修改文件：`src/study_coder/context.py`。

- `_summary_keys` 记录已经归纳的连续历史前缀，使用原始完整消息组的 SHA-256 校验摘要覆盖范围。
- `_working_view()` 将已覆盖前缀替换为 `_summary_text`，只追加尚未覆盖的消息组。
- `build_view()` 对工作视图计算 token，工具 schema 和活动技能仍计入预算；不再先计算整个归档历史的 token。
- `_summarized_view()` 保留最近两个完整消息组，推进摘要覆盖边界。
- `_summary_for()` 只将边界之后的新消息传给摘要器，并将旧摘要作为 previous 合并。不会再次提交已经归纳过的原始对话。
- 摘要输入中的工具输出可以裁剪；归档和覆盖校验仍使用完整原文。
- 规则摘要回退也只处理新增部分，同时保留原有摘要。
- 最终压缩会缓存压缩后的摘要和新边界，避免下一轮从较大的旧摘要重新开始。
- 历史被替换、缩短或已覆盖内容被修改时，缓存会明确失效；`/clear` 清空缓存。

工具请求及全部匹配结果始终作为完整消息组处理，摘要边界不会落在一组消息中间。

## 阈值和行为

窗口上限和原来的分级阈值保持一致：

1. 工作上下文小于窗口 50%：直接使用。
2. 否则裁剪工作上下文中的工具输出；裁剪后小于 70%：使用裁剪视图。
3. 否则生成增量摘要；摘要后小于 90%：使用摘要视图。
4. 否则进一步压缩已有摘要及新增的可移出消息；仍超过 90% 则明确报错。

例如历史原文已经有 20 万 token，但工作上下文只有 9 千 token：下一轮增加少量消息后，判断对象是“9 千＋新增消息＋固定提示/schema”，而不是重新使用 20 万历史作为触发条件。

新增不等于“刚上一轮生成”：上次摘要时保留的近期消息也尚未被摘要。它们会继续积累，等再次达到阈值后与后续新消息一起处理。
旧摘要仍作为摘要器的合并依据传入，但旧摘要覆盖的原始消息不再次发送。

## 日志

```text
[上下文压缩] 复用已有摘要：累计覆盖 172 组，未摘要 3 组
```

只说明复用缓存，不会因此调用摘要模型。

达到阈值时才出现：

```text
[上下文压缩] 开始摘要：仅处理 18 组未摘要消息
[上下文压缩] 摘要完成：累计覆盖 190 组旧消息
[上下文压缩] 工作上下文摘要：估算 ... → ... token（窗口 ...）
```

裁剪日志同样只统计工作上下文，避免把归档大小误认为当前模型输入大小。

## 会话与生效方式

完整 history 的会话保存方式不变。摘要缓存仍只存在于当前进程；恢复命名会话时会从完整历史按需重建一次摘要，此后再次按工作上下文预算增量处理。

修改的是宿主的上下文构造模块，重启 study-coder 后生效，无需为本次改动重新构建 Docker 镜像。
