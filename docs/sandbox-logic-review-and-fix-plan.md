## 3. 按严重程度展开

### 01 / P1：缺少跨进程互斥，恢复可能干扰正在进行的应用

**位置**：[apply_task / recover_task / cleanup_task](D:/study/Project/coder/src/study_coder/sandbox/docker.py:649)、[应用事务](D:/study/Project/coder/src/study_coder/sandbox/transfer.py:430)、[任务记录](D:/study/Project/coder/src/study_coder/sandbox/manifest.py:24)。

**原因与触发。** `save_record()` 用原子替换避免写出半份 JSON，但“读状态 → 判断 → 改文件 → 保存状态”整个过程没有锁。两个 CLI 进程可能同时处理同一个任务；不同任务也可能同时向同一个宿主工作目录应用结果。

尤其是 `apply_task()` 发现记录为 `applying` 时会调用恢复逻辑，它无法区分“上次进程崩溃”与“另一个进程正在正常应用”。进程 A 写入一半时，进程 B 可能把 A 当成中断任务并开始回滚；随后 A 仍继续写入或保存成功状态。清理也可能与导出、工具执行重叠。

**影响。** 宿主文件出现部分回滚、任务状态互相覆盖、备份或 staging 在使用中被删除。现有哈希校验可拦住一些冲突，但不能把完整事务变成串行操作。本次没有并发操作真实工作目录，竞争路径由代码确认。

**建议方案。**

1. 只增加一个小型跨进程锁上下文，Windows 使用 `msvcrt.locking` 的非阻塞模式，Linux 使用 `flock(..., LOCK_NB)`；锁文件初始化为至少一个字节，并固定锁同一位置。只将真实“锁被占用”映射成繁忙，权限 / I/O 错误保留原原因。
2. **获取策略固定为立即返回。** 第一版没有锁等待超时，也不新增 `--wait`、队列或轮询。冲突时返回非零退出码，并显示“任务正在使用中，请在原会话结束后重试”。会话持锁数小时是允许的，但其他命令不应跟着阻塞数小时。PID 可作提示，不能用于认定锁已失效。
3. **任务锁放在 `state_dir/<task_id>/.task.lock`。** runtime 在任务目录可见后、写首份记录前取得，持有到 finish / 取消收尾结束；异常退出由上下文关闭句柄。apply、recover、export、cleanup 的入口也必须先获取该锁再读状态。正常 finish 复用锁句柄，内部函数不递归加锁。只读 list 可展示原子记录，无需等锁；涉及 staging 的 review 以短任务锁读取，遇忙也立即返回。
4. **工作目录锁放在固定用户目录 `~/.study-coder/locks/workspace/<sha256>.lock`。** 键取 `normcase(str(workspace.resolve()))` 的哈希，不取可切换的 state_dir。仅在 apply / recover 修改宿主期间持有，不跟随整个模型会话持有；同用户不同任务的宿主写入因此串行。网络盘多主机协作不在第一版保证范围。
5. **锁文件保留复用，释放只关闭句柄。** 不能按锁文件年龄删除，也不在持锁期间 unlink；否则 POSIX 上可能产生两个 inode、两把不同的锁。当前 cleanup 保留任务记录，也保留 `.task.lock`；第一版不新增锁文件垃圾回收或自动破锁。
6. 固定先任务锁、后工作目录锁，内部 recover 复用已持有锁。取得锁后仍要检查 Docker 真实状态：进程崩溃会释放文件锁，但 daemon 中的容器未必停止，资源收尾由第 04 项处理。编辑器等外部程序不遵守本锁，现有哈希冲突检查必须保留。

**后续增强。** 只有确有需求时再增加有界等待、持锁进程详情和任务目录归档；不作为本轮锁修复的前置条件。

**验收。** 两个进程同时 apply 同一任务、两个任务 apply 同一目录、apply 与 cleanup 并发，都只能有一方进入事务；持锁进程崩溃后可以恢复；已有正在运行的任务不能被维护命令误判为待回收。

**代码量。** 最小层实现 70–110 行，测试 60–100 行；通过立即报忙和保留锁文件省去排队、超时及垃圾回收逻辑。锁范围与恢复正确性不能为了减行数省略。

### 02 / P1：工作区 Python 包可以替换 Worker 入口

**位置**：[Worker 启动](D:/study/Project/coder/src/study_coder/sandbox/docker.py:341)、[service runner 启动](D:/study/Project/coder/src/study_coder/sandbox/worker.py:245)。

**原因与触发。** 任务容器工作目录是 `/workspace`，入口执行 `python -m study_coder.sandbox.worker`。Python 的普通 `-m` 启动会把当前目录放入模块搜索路径。若项目包含同名包，或者任务写入了同名包，后续启动可能执行工作区版本。项目中的 `json.py` 等同名模块也可能干扰管理程序的导入。

**影响。** Worker 协议被破坏，工具无法运行；也可能伪造工具结果或绕过由 Worker 实现的容器内检查。Docker 的非 root、网络和容器资源限制仍然存在，不能据此声称已获得宿主权限。

**建议方案。**

1. 固定管理入口的解释器路径，例如镜像中的 `/opt/study-coder/.venv/bin/python`，以 `-I -B -m` 启动 Worker。`-I` 排除当前目录、用户 site-packages 和 `PYTHON*` 环境影响；`-B` 显式禁止字节码写入，因为 `-I` 会忽略 `PYTHONDONTWRITEBYTECODE`。
2. service runner 使用同样的启动方式。检查 doctor、代理等管理入口，直接修改现有 argv；只有确实消除重复才抽一个小函数，不新增通用启动框架。
3. 保持实际开发命令的正常工作目录和 Python 行为。隔离选项只加在沙箱管理程序入口，避免破坏项目自己执行 `python main.py` 的模块导入。
4. 重新构建镜像，并检查管理包来自只读安装目录。不要在隔离启动之后又手动把 `/workspace` 加回管理程序的 `sys.path`。

Python 的行为和 `-I` 选项见 [Python 3.12 命令行说明](https://docs.python.org/3.12/using/cmdline.html#cmdoption-I)。

**验收。** 工作区放置同名包、同名标准库模块和 `sitecustomize.py` 时，管理入口仍来自镜像；普通项目模块仍可被项目命令正常导入。需要补真实镜像验证，本次仅验证了本地 Python 的机制。

**代码量。** 新增实现 0–6 行，测试 20–35 行。主要改已有 argv，因此净新增可为 0；仍必须检查所有管理入口和重建镜像。

### 03 / P1：Windows 文件身份检查误报变化

**位置**：[文件身份与稳定打开](D:/study/Project/coder/src/study_coder/sandbox/transfer.py:99)。

**原因与触发。** `_file_identity()` 把设备、inode、大小、mtime、ctime 合成一个元组，然后直接比较 `Path.lstat()` 和 `os.fstat()` 的结果。当前 Python 3.12.3 执行环境下，对同一个未修改文件，前四项相同，`st_ctime_ns` 不同；`_read_stable_file()` 实际抛出 `file changed while opening`。

**影响。** 项目导入、宿主备份、staging 哈希检查和应用均可能在正常文件上失败。核心问题是跨 API 的字段可比性，换 shell 不会修复比较逻辑。本轮还观察到新建文件的两个 ctime 相等，所以不能声称任意文件、任意 Windows / Python 版本必现。

**建议方案。**

1. `_file_identity()` 明确返回 `(st_dev, st_ino, st_size, st_mtime_ns)`，用于路径与句柄之间的比较。**不变量：跨来源身份元组永远不含 ctime。** 当前 CPython 已提供需要的文件标识，第一版不写 Win32 封装、不新增依赖。
2. 同一描述符读取前后的变化检查，额外比较 `fstat` 的 `st_ctime_ns`；路径前后若比较 ctime，也必须是相同 API。将这些同源比较加回 `_read_stable_file/_file_hash/_copy_stable_file` 对应位置，避免移除跨来源 ctime 时一并降低已有检测能力。
3. 保留类型、链接 / reparse point、读取长度和内容哈希验证。不要改用 `DirEntry.stat()` 缓存结果充当文件身份；在 Windows 上它的部分标识字段与 `os.stat/fstat` 不同。若实际文件系统返回不可用标识，明确拒绝该路径，先不为假想平台增加兼容层。

CPython 在 Windows 可用时将文件索引填入 `st_ino`；与 `st_dev` 组合用于标识文件。时间字段仍受版本和文件系统影响，参考 [Python 3.12 stat_result 说明](https://docs.python.org/3.12/library/os.html#os.stat_result)。这里直接使用现有标准库字段，既无需 Win32 封装，也不将四字段比较夸大为完全防御恶意文件系统竞态。

**验收。** 分两层：一条不依赖平台的单元测试构造前四字段相同、ctime 不同的两个元数据对象，要求身份相等；再改变 inode / size / mtime，要求不相等。Windows 实文件测试直接比较 `_file_identity(path.lstat())` 与 `_file_identity(os.fstat(fd))`，用 `try/finally` 关闭 fd，不要求原始 ctime 必须不同。另测同句柄读取前后变化仍被拒绝，恢复批次 A 的正常导入 / 应用测试。这样确定性验证的是程序不变量，而不是赌某台机器能产生某种时间差。

**代码量。** 实现 8–18 行，测试 25–45 行。直接修改身份元组并补同源检查，不增加平台适配框架。

### 04 / P1：生命周期中断后可能遗留容器和中间状态

**位置**：[启动清理](D:/study/Project/coder/src/study_coder/sandbox/docker.py:314)、[导出器创建](D:/study/Project/coder/src/study_coder/sandbox/docker.py:537)、[导出错误处理](D:/study/Project/coder/src/study_coder/sandbox/docker.py:577)、[CLI 执行及 finish](D:/study/Project/coder/src/study_coder/cli.py:176)。

**建议方案。**

1. 优先扩大已有 `try/finally` 保护区，纳入进程创建、管道、线程和 watchdog；局部变量初始化为 `None` 后按是否成功创建收尾。对 Ctrl+C 收尾后重新抛出，不引入新的生命周期框架。
2. 为临时辅助容器设置唯一名称和可验证标签，创建前记录计划资源。doctor 的独立预检可使用独立探测 ID，并在自身 `finally` 中回收。
3. 清理时同时处理宿主 CLI 和 daemon 中的容器，确认容器停止后才判断卷是否可安全导出或删除。每个资源独立尝试回收，汇总错误，避免一个失败阻断其余清理。
4. 区分启动失败与已有成果的运行 / 导出失败。后者默认保留 volume，清除未发布的 staging，记录 `export_failed` 和可重试原因；不能为了“清理干净”丢弃未导出的成果。
5. CLI 用统一生命周期边界保证模型调用、会话保存和用户中断等出口均收尾。对进程强制终止、断电等无法执行 `finally` 的情况，下次启动依靠记录和 Docker 实际状态协调恢复。

**验收。** 在创建卷、导入、启动代理、启动任务、创建导出器和读取 tar 的位置注入普通异常、进程创建失败、Ctrl+C，均有可解释的终态；已存在成果可重试导出；无归属标签的资源不被删除。

**边界。** 复用现有记录与 export / cleanup 命令处理下一次恢复；自动扫描全部历史任务并回收的后台机制留到后续，不是当前闭合异常路径的必要条件。

**代码量。** 实现 35–60 行，测试 45–75 行；主要调整现有异常边界和复用归属清理函数。

### 07 / P2：配额扫描定义不同，并忽略错误

**位置**：[Worker 扫描](D:/study/Project/coder/src/study_coder/sandbox/worker.py:92)、[服务扫描](D:/study/Project/coder/src/study_coder/sandbox/service_runner.py:16)、[导入及导出预算](D:/study/Project/coder/src/study_coder/sandbox/transfer.py:148)。

**兼容性提醒。** 不能直接把 `files += 1` 扩展到所有目录后仍用同一个 50,000 上限。成员上限虽减少空目录滥用，也不会变成 volume 硬配额；新拒绝行为必须明示。

**验收。** 相同树在 Worker / runner 统计一致；大量空目录、权限拒绝、链接和并发删除均得到定义好的结果；监控失效不会被当成配额检查成功。

**代码量。** 最小层净新增实现 25–45 行，测试 35–60 行。共享函数挪动和删除重复实现不重复计数；完整统计模型与独立目录配置留待后续。

### 09 / P2：代理空闲期限与完整请求期限存在缺口

**位置**：[请求头读取](D:/study/Project/coder/src/study_coder/sandbox/network_proxy.py:44)、[DNS 与连接](D:/study/Project/coder/src/study_coder/sandbox/network_proxy.py:158)、[TLS 首包](D:/study/Project/coder/src/study_coder/sandbox/network_proxy.py:196)、[转发循环](D:/study/Project/coder/src/study_coder/sandbox/network_proxy.py:264)。

**原因与触发。** `_relay()` 设了 socket timeout，但没数据时 `select()` 返回空列表，代码直接继续，没有执行会触发该 timeout 的 `recv()`。真正起作用的是转发阶段总期限，默认 1,800 秒。请求头和 ClientHello 的多次读取只有单次等待限制；缓慢持续发字节可以拖长整个阶段。DNS 和多地址连接也没有共享请求截止时间。

**影响。** 闲置或缓慢连接长期占用线程。代理容器只有有限的进程 / 线程与内存预算，正常请求可能因容量被占用而失败。已有总期限意味着 relay 并非完全无限等待，应准确表述为“空闲期限失效、整条请求缺少统一期限”。

**建议方案。**

1. 最小层先修已复现的 relay：记录 `last_activity`，在 `select` 无数据时也检查空闲期限；等待时间取空闲剩余与总剩余的最小值，仅成功转发字节后更新活动时间。
2. 把已有 `max_duration` 的起点前移到 `handle`，在请求头、TLS 握手、多地址连接和转发之间共用 deadline。每次 `recv/sendall/connect` 前将 timeout 收紧到剩余期限；现有头部 / ClientHello 字节限制保留，不新增通用网络框架。
3. 将请求头读取移入现有错误处理范围，确保超时可正常收尾；上游 socket 由一个 `finally` 负责关闭，不用多份清理分支。
4. **明确尚未解决的 DNS 阻塞。** 同步 `getaddrinfo()` 无法仅靠上述 socket timeout 获得硬期限。最小层在调用前后检查 deadline，防止返回后继续处理已过期请求，但不能保证 DNS 调用期间线程被按时释放。此项整体只能标为“已止损，DNS 期限仍开放”。

**后续增强。** 如需要整个请求的严格等待上限，再增加有界 DNS 执行器、排队和连接并发控制；取消等待不等于取消 OS 解析，不得不断产生替代线程。原完整方案实现 70–120 行、测试 90–150 行作为另一层预算参考，不与本层机械相加。

socket timeout 针对阻塞 socket 操作的语义见 [Python socket 文档](https://docs.python.org/3.12/library/socket.html#socket.socket.settimeout)。

**验收。** 无数据、慢请求头、慢 ClientHello、持续有效下载、多地址连接失败和慢接收方均受相应 deadline 约束，活动下载不被误判为空闲。DNS 延迟返回后禁止继续转发；DNS 永不返回作为已记录剩余缺口，不能将该场景登记为最小层已通过。

**代码量。** 最小层实现 20–40 行，测试 30–55 行；减少的是范围，不是删掉必要的 socket 关闭或超时验证。

### 10 / P2：宿主和镜像 Worker 没有版本与能力握手

**位置**：[doctor](D:/study/Project/coder/src/study_coder/sandbox/docker.py:121)、[请求发送](D:/study/Project/coder/src/study_coder/sandbox/docker.py:434)、[Worker 请求解析](D:/study/Project/coder/src/study_coder/sandbox/worker.py:433)。

**原因与触发。** doctor 仅检查模块可导入，没有确认协议版本、支持的工具或限制字段。宿主更新源码但未重新构建镜像时，镜像内旧 Worker 仍可能通过检查。固定 image ID 保证同一次任务使用固定镜像，并不保证它和当前宿主协议兼容。

**影响。** 新工具被拒绝、新增限制字段被旧版本忽略、响应字段不匹配；错误发生在任务中途而非启动前。

**建议方案。**

1. 在已有共享模块加入单个 `PROTOCOL_VERSION` 整数。第一版要求宿主与镜像版本严格相等，暂不设计能力集合、版本区间和兼容矩阵；只在协议或关键限制语义变化时递增。
2. doctor 的现有可信检查顺便打印版本，宿主解析验证后再创建卷。旧镜像没有常量、返回损坏或版本不同，统一明确提示重建镜像，而非继续任务。
3. 请求 / 响应带相同版本，Worker 和宿主各验证一次；任务记录增加该值便于恢复诊断。复用现有 JSON 通道，不增加单独的常驻握手服务。

**后续增强。** 需要同时兼容多代镜像时，再增加按能力协商。严格版本相等虽然要求及时重建镜像，却能用较小改动阻止旧代码静默忽略关键字段。

**验收。** 版本相同可启动；版本不同、缺版本和错误输出在任务循环前拒绝；每次请求版本不符也被拒绝。不要求第一版支持不同版本之间的协商。

**代码量。** 最小层实现 15–30 行，测试 20–35 行。真实旧 / 新镜像仍需集成验收。

### 11 / P2：容器可生成、却无法导出的单文件大小

**位置**：[传输常量及导出校验](D:/study/Project/coder/src/study_coder/sandbox/transfer.py:22)、[Worker 配额](D:/study/Project/coder/src/study_coder/sandbox/worker.py:92)、[策略](D:/study/Project/coder/src/study_coder/sandbox/policy.py:17)。

**原因与触发。** 导入与导出将单文件固定限制为 16 MiB；运行阶段主要限制总字节数和文件数，默认总量为 1 GiB。一个 20 MiB 的交付文件可能满足运行预算，但在任务收尾时被拒绝导出。

**影响。** Agent 报告生成成功，最终成果无法交付。单文件限制本身合理，问题是它没有作为统一且提前可见的交付约束。

**建议方案。**

1. 最小层保留现有 16 MiB 常量，执行与传输引用同一常量；不增加可配置限额，不改变已有快照格式。
2. 在第 07、08 项扫描与最终检查中，对可交付文件检查该限制。复用传输排除判断，并把现有 `policy.exclude` 传给 Worker / runner；不能只识别默认排除，误杀用户明确排除的大文件。
3. 超限反馈包含路径、大小、16 MiB 限额和调整产物的建议。文件工具可复用现有写前大小估算；命令仍在结束前检查，宿主导出仍独立校验。
4. 依赖和缓存仍计入运行总字节预算；忽略其交付单文件上限不等于不计磁盘用量。系统提示明确当前交付限制，不暗示用户已有尚未实现的环境配置开关。

**后续增强。** 自定义单文件限额和超大文件流式导入一起评估，不能只提高常量而保留无界内存读取。最小层恢复的是提前报错的一致性，仍不支持交付超过 16 MiB 的单文件。

**验收。** 阈值以下、恰好阈值、超过阈值、默认排除与用户额外排除的大文件处理一致；超限交付文件在执行阶段就有清楚反馈，无需等最后导出才发现。

**代码量。** 最小层实现 15–30 行，测试 25–40 行，按复用第 07 项扫描估算。自定义限额与流式导入不计入。

### 12 / P2：服务启动等待固定为 20 秒

**位置**：[服务参数 schema](D:/study/Project/coder/src/study_coder/tools/sandbox_service.py:20)、[启动等待](D:/study/Project/coder/src/study_coder/sandbox/worker.py:259)、[宿主工具超时选择](D:/study/Project/coder/src/study_coder/sandbox/docker.py:444)。

**原因与触发。** `_start_service()` 写死 20 秒。首次编译或初始化时间超过 20 秒的合法服务，会被停止并返回失败。模型没有可调的启动等待参数；宿主又把非 bash 工具统一放在 `settings.command_timeout_s` 内，即使只改 Worker 的 20 秒，也可能先被宿主 watchdog 取消整个容器。

**建议方案。**

1. 为工具增加可选 `startup_timeout_s`，默认保留 20 秒；第一版复用已有 `policy.max_command_timeout_s` 作为宿主上限，暂不新增独立环境变量和策略字段。
2. schema、宿主参数验证、Worker 请求解析和 `_start_service()` 使用同一值，错误信息显示实际采用的期限。
3. 宿主等待预算按“启动等待 + 有界清理时间 + 协议传输余量”推导；不能仍然固定使用普通命令的 60 秒。所有上限在宿主验证，不能只信任 Worker 参数。
4. 启动过程中继续检查进程存活和资源预算；超时后清理进程组，并避免发布一个无法停止的服务记录。

**验收。** 服务 25 秒就绪时，默认 20 秒失败，显式 40 秒成功；请求超过宿主上限被拒绝；小的普通命令超时不误杀已批准的较长服务启动；启动失败无孤儿进程。

**代码量。** 实现 15–30 行，测试 20–35 行。只传递一个参数并联动现有 watchdog；独立服务策略、日志采集等扩展不包含在本项。

### 13 / P3：默认排除规则没有覆盖 .cache

**位置**：[共享排除规则](D:/study/Project/coder/src/study_coder/sandbox/transfer.py:26)。

**原因与触发。** `HOME=/workspace` 使部分工具把缓存放到 `/workspace/.cache`。当前列表包含 `.npm`、`.uv-cache` 等，却没有 `.cache`。在当前“不导出开发缓存”的设计下，这是覆盖缺口；不能一般性断言所有项目名为 `.cache` 的目录都没有业务意义。

**影响。** 缓存中的链接触发不支持类型错误，较大文件触发单文件限制，大量文件增加传输负担。本次构造 `.cache/tool/link` 已复现整个导出失败。

**建议方案。**

1. 在 `_EXCLUDED_PARTS` 中增加 `.cache`。`tar_exclude_patterns()` 已从该集合生成，因此导入、tar 导出预过滤和宿主最终过滤能一起生效。
2. 加根目录与嵌套目录测试，例如 `.cache/...` 和 `frontend/.cache/...`，验证其链接不会进入交付类型检查。
3. 保持其他未排除路径上的链接与大小检查。不要通过放宽全部链接校验解决缓存问题。
4. 说明这一默认目录名是保留的缓存位置。若未来需要导出名为 `.cache` 的业务目录，再设计可覆盖排除策略，不为本次增加新配置。

**验收。** GNU tar 参数与宿主过滤都覆盖 `.cache`；正常源文件和 `.env.example` 仍保留；排除目录中的数据仍受实际传输流预算保护，不能通过直接向解析器发送任意大 tar 绕过防护。

**代码量。** 新增实现 0–2 行，测试 10–20 行；在已有集合所在行直接加成员可能净增 0 行。

## 5. 完成标准与不应夸大的结论

- 修复时补充能够证明行为的回归测试，而非只断言新增配置字段存在。
- 文件与事务类测试同时覆盖正常操作、故障中断和恢复；用临时工作目录验证，不触碰真实用户成果。
- Windows 身份检查围绕跨 API 可比性与同源变化检测验收；用构造元数据验证不变量，再做实文件与 Linux 回归，不以切换 shell 代替问题验证。
- 容器入口、进程清理、真实服务和网络 deadline 需要 Docker 集成验证。单元测试替身通过不能替代这些验证。
- 本清单没有实现 volume 硬磁盘配额、内核级隔离增强或对所有恶意同 UID 进程的管理程序保护。这些不是几行逻辑补丁能够完成的工作，也不包含在估算里。
- 最小层通过后逐项标记“已修复”“提前拒绝不支持的操作”或“部分止损、仍有缺口”，不能笼统写成 13 项已完全解决。06 尚不支持自动转换，09 的同步 DNS 硬期限仍开放；其他后续增强也不应计入当前完成量。
